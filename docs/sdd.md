## 1. High-level architecture

```
┌──────────────────────────── CLIENT (Flutter app) ────────────────────────────┐
│  Presentation:  Library │ Editor(canvas+docks+outline) │ Scene │ Setlists    │
│  State:         Riverpod-контроллеры, ToolStateMachine, GestureArbiter       │
│  Application:   UseCases (ImportIReal, TransposeSong, BuildSetlist, Share…)  │
│  ┌─────────────────────────── chart_core (pure Dart) ─────────────────────┐  │
│  │ Song-модель │ ChordGrammar │ Transposer │ LayoutEngine │ IRealCodec │  │
│  │ OpLog (event-sourcing) │ SpellingTable │ SetlistModel │ FileFormats │  │
│  └────────────────────────────────────────────────────────────────────────┘  │
│  Infrastructure:  storage_drift (SQLite) │ ink_native (federated plugin) │   │
│                   pdf_export │ telemetry (LDD sinks) │ share_service        │
│  Native modules:  ink_native_ios (PencilKit) │ ink_native_android (InkView) │
└──────────────────────────────────────────────────────────────────────────────┘
        │ v1: НЕТ сервера (local-first, шеринг файлами .chart/.setlist)
        │ v1.5: SyncService (контракт зафиксирован сейчас, реализация позже)
┌───────▼──────────────────────── BACKEND (v1.5, контракт сейчас) ─────────────┐
│  Sync API: pushEvents/pullEvents/getSnapshot/createShareLink (append-only)   │
│  Postgres (docs, events, blobs) + auth magic-link; за интерфейсом SyncService │
│  Telemetry ingestion: POST /v1/events (batch jsonl); v1 = LocalFileSink       │
└──────────────────────────────────────────────────────────────────────────────┘
```

**Ключевое:** весь домен живёт в `chart_core` без зависимостей от Flutter/SQLite → тестируется
на ПК без устройств, переиспользуется сервером в v1.5 для валидации событий.

## 3. Данные: схемы и форматы

### 3.1 Op-log (ядро event-sourcing, D6)

```json
{"v":1,"seq":42,"deviceId":"…","ts":"…","type":"chord.insert",
 "anchor":{"sectionId":"s1","bar":3,"beat":1.0},
 "payload":{"root":"C","quality":"m7","alt":[],"slash":null,"paren":false},
 "inverse":"chord.delete"}
```

- Undo/redo = append inverse-события (аудит бесплатно); redo-стек в памяти.
- Snapshot = свёртка событий до `seq N`; хранение: snapshot + хвост событий.

### 3.2 SQLite (drift)

`documents(id,title,key,bpm,updated_at,snapshot_json,snapshot_seq)` ·
`document_events(doc_id,seq,device_id,ts,type,json) idx(doc_id,seq)` ·
`ink_blobs(id,doc_id,anchor_json,format,path)` · `setlists(id,title)` ·
`setlist_items(setlist_id,pos,doc_id,transpose_sem,notes)` · `meta(k,v)`.

### 3.3 Файлы шеринга

`.chart` / `.setlist` = ZIP: `manifest.json` (format, v) + `snapshot.json` +
`events.jsonl` (хвост) + `ink/*.bin`. Импорт = merge событий; конфликт версий формата →
явная ошибка с логами, не молчаливая порча.

### 3.4 Anchors (D3)

Аннотация = `{anchor:{sectionId,bar,beat,step?}, offsetLocal, kind:ink|stamp|cue, payload}`.
Координаты вычисляются LayoutEngine-ом из bbox цели → переживают транспозицию/reflow/reorder.

## 4. Frontend: пайплайны рендера и ввода

**Layout:** `Song → SectionPlanner (play-order для сцены; edit показывает структуру со знаками) →
BarLayout (ширины по контенту) → SystemBuilder → PageBuilder → PageLayout`. Кэш: layout секции
keyed by `(sectionId, contentHash, widthBucket)`; рендер страницы = `ui.Picture`-кэш,
инвалидация по событиям, затронувшим страницу. Цель S4: < 16 мс/страница.

**Editor state:** `ToolStateMachine {SELECT, INPUT(chord|note|structure|stamp),
INK(pen|hl|eraser)}` + `GestureArbiter` (pen→ink, 1 палец SELECT→pan, 2 пальца→zoom/pan всегда)
+ курсор вставки с auto-advance + sticky-параметры (D2).

**Ink overlay:** PlatformView внутри того же transform-узла, что и canvas (единая Matrix4
scroll/zoom; Android — Hybrid Composition).

Контракт плагина зафиксирован в `ink_native_platform_interface`:
`initialize/setTool/setTransform/loadStrokes/exportStrokes` + поток
`onStrokeCommitted(blobId, bboxCenter)` → app вычисляет anchor от bboxCenter. Штрихи хранятся в
anchor-local координатах.

**State management:** Riverpod (code-gen, тестируемость). Решение A1.

## 5. Backend: v1 = интерфейс, v1.5 = реализация

- `SyncService` (interface в application layer): `pushEvents(docId,fromSeq,events[])`,
  `pullEvents(docId,afterSeq)`, `getSnapshot`, `createShareLink`. v1-имплементации:
  `NullSyncService`, `FileShareService` (.chart через системный share-sheet).
- v1.5: Postgres-append-only логов + magic-link auth; рекомендация — Supabase-совместимая схема
  за интерфейсом (возможен self-host). Конфликты: per-doc «чужие события поверх», UI-merge позже.
- **Telemetry (LDD):** `TelemetrySink` interface; v1 = `LocalFileSink` (rotating jsonl, батч при
  сохранении, sampling в bench-режимах) + отключаемый `HttpSink`. Никакой персональной
  информации: только события редактора и метрики.

## 6. Пайплайн тестирования

| Уровень | Что | Инструмент | Gate |
|---|---|---|---|
| L0 unit | chart_core: транспозер (property: round-trip 12 ключей), chord-grammar, codec-fuzz, op-log merge | dart test | coverage core ≥ 90%, CI-block |
| L1 golden | рендер фикстур 3 эскизов → PNG | flutter golden | pixel-diff = 0 (шрифт pinned) |
| L2 widget/integration | **tap-бюджеты как тесты**: «диатонический аккорд = 1 тап», «нота = 1 тап», вольта = ≤2 | flutter_test + patrol | fail при превышении бюджета |

## 7. Developer environment

`bootstrap.ps1` (Windows) и `bootstrap.sh` (Linux/macOS) выполняют одни и те же шаги в одном
порядке и печатают `KEY=VALUE`, поэтому упавший bootstrap называет конкретный шаг:

```
GIT=2.51.2.windows.1
FLUTTER=3.47.7 (fvm-link)
DART=3.13.5
JDK=17
ANDROID_SDK=ok (C:\src\android-sdk)
WORKSPACE=ok
VERIFY=pass
BOOTSTRAP=ok
```

Шаги: Git (+`core.longpaths` на Windows) → Flutter пинованной версии из `.fvmrc` → Dart (идёт в
SDK) → JDK 17 → Android SDK → резолв workspace → `melos run verify`.

Скрипты **ничего не скачивают**: установка SDK — намеренное действие, поэтому bootstrap
сообщает, чего не хватает, и печатает команду исправления. Идемпотентны.

**Команды:**

| Команда | Что делает |
|---|---|
| `melos run verify` | Приёмочный gate: lint + format-check + тесты |
| `melos run lint` | Только статический анализ |
| `melos run format-fix` | Привести файлы к форме `dart format` |
| `melos run test-dart` | Тесты пакетов, которым Flutter не нужен |
| `melos run test-flutter` | Widget/golden-тесты Flutter-пакетов |
| `dart run logview <file.jsonl> --metric <path> --agg p50,p95` | Отчёт по bench-логу |

Конвенция коммитов: `feat(core-transposer): …`; ветки `feat|fix|spike/<pkg>-<task>`.

**DoD агента:** `melos run verify` зелёный + логи приложены + inline-контракт обновлён тем же
изменением + ADR не требуется (см. журнал решений).

## 9. Журнал решений

Два пространства имён, и их важно не смешивать.

**D-номера принадлежат владельцу продукта.** Это решения о продукте: что делаем, для кого и с
какими границами. Диапазон **D1–D19** занят (таблица ниже). Диапазон **D20 и выше** зарезервирован
за новыми решениями — сюда попадает только то, что владелец утвердил как изменение продукта.

**A-номера принадлежат исполнителю.** Это решения о реализации и инструментах: как именно
устроено то, что владелец уже решил, и какие ограничения среды это вынудило. Они не меняют
продуктовых границ и не требуют утверждения, но фиксируются, потому что каждое из них кто-то
однажды захочет пересмотреть.

Изначально обе категории лежали в пространстве D — отсюда столкновение номеров, когда пришёл
ADDENDUM с авторитетным реестром D1–D19. Перенумерация выполнена один раз и полностью: 23 записи
исполнителя стали A1–A23, имена в тексте обновлены, диапазоны больше не пересекаются.

### D20 — дистрибуция веб-версией, нативный ink остаётся качеством для пера

**Решение владельца, принято 2026-10-10.** Меняет форму D4 и D5, не отменяя их целей.

Приложение распространяется **веб-страницей** как основным каналом: одна ссылка, устанавливаемая
на домашний экран как PWA в режиме `standalone`. Ядро (`chart_core`) и интерфейс остаются
Flutter-овыми и общими для всех носителей; **нативный ink сохраняется как путь качества** там, где
есть настоящее перо (Android + S Pen сейчас, PencilKit на iPad — когда появится устройство).

**Почему.** Разработка ведётся из России, и это закрывает оба магазина: платная регистрация Apple
для российских разработчиков падает на оплате, а Google ограничивает публикацию для российских
разработчиков. Веб не требует ни аккаунта, ни Mac, ни модерации, ни подписи — и одинаково
работает на iPhone, Android и десктопе. Прецедент на уровне эталона: **Goodnotes сам поставляет
веб-версию**, то есть рукопись в браузере жизнеспособна у продукта, который заказчик назвал
образцом.

**Что в вебе достижимо, а что нет.** Pointer Events дают `pointerType` (перо отличимо), `pressure`,
`tilt`, `size`, `distance` и `getCoalescedEvents()`. Модель указателя Flutter несёт те же величины
(`PointerEvent.kind/pressure/tilt/size/distance`). Чего в вебе НЕТ: PencilKit и его сглаживания,
front-buffered рендеринга Android и API момента показа кадра. Последнее означает, что замер
задержки в вебе слабее нынешнего нативного, и это принимается сознательно: задержка не является
приоритетом продукта.

**ИСПРАВЛЕНО ПО ЗАМЕРУ, а не по рассуждению — И ЗАТЕМ ИСПРАВЛЕНО ВТОРОЙ РАЗ.** Здесь было
написано, что «правило ладони переносится прямым счётом». Это неверно. Но **и моя первая попытка
исправить это тоже была неверной**, и вот почему её стоит прочитать.

**Прогон 1** (перо в игре: 1263 сэмпла пера, 215 событий наведения): ширины касаний легли в
диапазон `1..8`, перо ширину не сообщило вовсе. Из этого я заключил, что браузер геометрию контакта
**не отдаёт**, и записал правило «пока перо рядом — игнорировать касания». **Вывод был сделан по
одному прогону и оказался неполным.**

**Прогон 2** (пера не было вообще: `penSeen 0`): ширины касаний — `2,3,4,6,7` **И `71`, `87`**.
То есть браузер ширину **отдаёт**, и ладонь даёт тот же порядок величины, что на Android (там 86–91).
Разделение огромное: `1..8` против `71..87`.

**Чего эти два прогона НЕ различают**, и что нельзя закрыть рассуждением: широкие касания в первом
прогоне могли отсутствовать по двум причинам — **либо ладонь не лежала на стекле, либо платформа
подавила её, пока активно перо**. Числа не позволяют выбрать, и делать вид, что позволяют, было бы
ровно той ошибкой, которую здесь исправляют.

**Поэтому правило берёт ОБА сигнала**, и каждое отклонение записывает, **какой сигнал сработал**:

| Условие | Что делает |
|---|---|
| перо видели в пределах окна | игнорировать касание |
| иначе ширина касания ≥ 40 CSS px | игнорировать касание |
| иначе | это палец, он рисует |

Порог 40 лежит между наблюдаемыми группами. Проверено вождением все три случая: узкое касание без
пера рисуется, широкое отклоняется по ширине, узкое сразу после пера отклоняется по приближению.
Окно «рядом» по-прежнему должно быть **измерено** по промежуткам между событиями пера, а не
назначено, и страница теперь печатает эти процентили.

**Пользовательские данные — ФАЙЛАМИ, а не в хранилище браузера.** Кнопки сохранения и открытия;
на Chrome/Android — File System Access API с перезаписью на месте, на Safari/iOS — выбор файла и
скачивание. Это снимает документированное поведение Safari: хранилище и service worker чистятся
через 7 дней неиспользования, и исключение только одно — установленное приложение в режиме
`standalone` (WebKit 232302, WONTFIX). При файловом хранении эта чистка забирает **кэш**, а не
ча́рты. Хостинг раздаёт только статику и не хранит пользовательских данных вообще.

**ПОПРАВКА К ЭТОМУ АБЗАЦУ, ПОЛУЧЕННАЯ ПРИ РЕАЛИЗАЦИИ.** «Chrome/Android» здесь неточно:
`showSaveFilePicker` существует **только в настольном Chromium**, и **Chrome на Android его не
имеет**. То есть на планшете Android перезаписи на месте не будет — приложение честно определит это
и будет скачивать новый файл на каждое сохранение, сказав об этом в интерфейсе. Определение идёт по
наличию метода на объекте `window`, а не по строке user-agent, поэтому планшет попадает в ветку
скачивания сам, без правки кода. Это не отменяет D20 — данные по-прежнему файлами, и по-прежнему
локально у владельца, — но обещание «перезапись на месте» верно только для настольного Chrome.

**Инвариант, который держит всю схему:** канонический поштриховой формат (O2) — общий для всех
реализаций шва. Ча́рт, написанный в браузере, открывается нативным приложением и наоборот, а запись
в веб-версии — это **третья реализация одного шва** `ink_native_platform_interface`, а не второй
продукт.

**Что решает вопрос окончательно.** Доживают ли до страницы высокочастотные сэмплы Apple Pencil и
заполнены ли `pressure`/`tilt` на iOS — **не подтверждено** (форум Apple недоступен, у WebKit есть
баг в `getCoalescedEvents`). Это измеряется спайком: одна страница, прогон на планшете с Chrome и на
iPhone с Safari, сравнение с уже снятыми нативными числами Android. До этого числа веб — принятый
канал распространения, а не заявленное равенство по качеству пера.

Вынужденное: `flutter_test` в Flutter 3.47.7 требует `test_api 0.7.12` **точно**, и только

### A6 — `storage_drift` без `sqlite3_flutter_libs`

cold-open против порога 1000 мс.

### A7 — desktop-таргеты (Windows и Linux) в `apps/mobile`

Причина: S4 требует отклика < 16 мс/страницу, и живой отклик на ПК ускоряет итерацию по layout
без эмулятора. Ограничение: `PlatformView`-ink на десктопе не работает; app-facing пакет
`ink_native` регистрирует no-op реализацию, а редактор читает `supportsInk` и не предлагает
ink-инструменты.

### A8 — модель аккорда: класс высоты + явное предпочтение написания + `SpellingTable`

Выбрано владельцем проекта из трёх вариантов. Корень аккорда хранит звучащую высоту
(`pitchClass`) и необязательное `SpellingPreference` (`automatic | sharp | flat`); письменная
форма не хранится, а **вычисляется** функцией `SpellingTable.spell(pitchClass, key, preference)`.

Причина, по которой это важно, а не косметика: написание — чистая функция от трёх входов,
поэтому круговой обход 12 ключей возвращает исходное написание **по построению**, а не по
совпадению. Если бы корень хранил букву и альтерацию и переписывался по буквенным шагам,
замкнутость зависела бы от истории преобразований. Альтернатива «только класс высоты» отброшена:
она теряет замысел композитора (bVI перестаёт быть bVI).

Отвергнуто: хранение написания в корне и диатоническое транспонирование по буквам — даёт
замкнутость, но один и тот же аккорд в разных контекстах пишется по-разному, а таблица не нужна.

### A9 — хроматические ноты в тональности без знаков пишутся с бемолями

Документированное упрощение. Правило: диатонические ступени берутся из знаков тональности (там
предпочтение не действует вообще); для остальных пяти классов высоты выбирается написание с
наименьшим числом знаков, затем — по направлению тональности (`fifths > 0` → диезы, иначе
бемоли). Тональность без знаков (C major, A minor) попадает в ветку бемолей.

Причина: единое направление не может быть верным для всех шести хроматических нот. В C major
традиция смешанная — bII, bIII, bV, bVI, bVII пишутся с бемолями, а #IV с диезом. Бемоли верны
для пяти из шести, диезы — для одного из шести. **Известное отклонение: #IV в C major даёт `Gb`
вместо `F#`**; это зафиксировано тестом `the tritone above the tonic is a documented deviation`,
чтобы изменение правила было осознанным решением, а не сюрпризом. Escape hatch — явное
`SpellingPreference` на аккорде. Полный учёт контекста требует гармонического анализа, которого в
проекте нет; догадка, одетая в правило, была бы заметно хуже записанного ограничения.

### A10 — `scaleOf` применяет минорный интервальный шаблон к минорным тональностям

Исправление бага, найденного спайком S3. Первая реализация применяла мажорный шаблон
`[0,2,4,5,7,9,11]` от любой тоники, поэтому для E minor возвращала ноты **параллельного мажора**
(E F# G# A B C# D#) вместо натурального минора (E F# G A B C D), и аккорд, принадлежащий
тональности, сверялся бы со шкалой, которой в этой тональности нет. Теперь шаблон выбирается по
`Mode`: `[0,2,4,5,7,9,11]` для мажора и `[0,2,3,5,7,8,10]` для минора.

Причина, по которой это стоит записи: баг не проявлялся ни на одной мажорной тональности, а
спайк S3 гоняет только мажорный цикл. Его поймал отдельный тест `scaleOf` на A minor и E minor.

### A11 — gate усилен: `public_member_api_docs` переведён в `warning`

Найдено при проверке, а не при написании. `dart analyze` возвращает **0**, когда видит только
замечания уровня `info`, а этот линт по умолчанию именно `info`. То есть требование
«документация — часть контракта» **не было ничем обеспечено**: анализ печатал «2 issues found» и
выходил с кодом 0, а `melos run verify` отчитывался SUCCESS.

Теперь правило объявлено `warning` в `analysis_options.yaml`, и gate падает. Проверено
фальсификацией: с внесённым нарушением `dart analyze` вернул 2, после удаления — 0.

`todo` намеренно оставлен `info`: TODO разрешены, но должны быть видимы, и валить из-за них
сборку не нужно.

### A12 — структура ча́рта: секция → такты, маркеры на тактах

Выбрано владельцем проекта из трёх вариантов (против иерархии `RepeatGroup`/`VoltaGroup` и
против плоского потока токенов). Секция содержит список тактов; каждый такт несёт **свою**
длину, размер, тактовые черты, номер вольты, маркер «повторить предыдущий такт/два», слэш-повтор,
метку N.C. и знаки (segno/coda/фермата/остановка игрока).

Причина: якорь аннотации адресуется как `{sectionId, bar, beat, step?}`. При плоском списке
тактов внутри секции адрес такта — это одно число. В иерархии тот же адрес стал бы путём из
нескольких индексов, и вставка одного такта переписывала бы структуру вокруг него, отвязывая все
аннотации. Размер хранится на такте, а не на песне, потому что в реальных ча́ртах он меняется
внутри песни: песенная константа заставила бы импортёр выдумать «значение по умолчанию» и затем
потерять каждое изменение.

`Volta(0)` — это **безымянная** скобка (`N0`), и это отличается от отсутствия скобки (`volta ==
null`). Поля-признака с тремя состояниями не заводится: `null` означает «нет скобки».

### A13 — хранится только написанная форма; порядок исполнения — производное

Выбрано владельцем проекта. `Song` не содержит развёрнутого порядка. Повторы, вольты и навигация
записаны в тактах, а развёртка — чистая функция над этим значением.

Причина: два представления одной музыки рано или поздно разойдутся на отредактированном ча́рте, и
не останется способа понять, какое из них читает музыкант. SDD требует и структуру (edit), и
порядок (Scene) — но требование иметь оба **представления** не означает хранить оба.

Следствие, зафиксированное как пробел: сама функция развёртки ещё не написана. Повторы, вольты и
размер уже смоделированы и покрыты тестами; навигация (`D.C. al Coda`, `D.S. al Fine`, кода,
фине) распознаётся только как сохраняемый дословно текст `<…>` на такте и будет интерпретирована
вместе с развёрткой. Причина отложить: разведка показала, что обработка навигации различается
между реализациями, а корпуса для проверки у нас нет.

**ПРОБЕЛ ЗАКРЫТ ЧАСТИЧНО — см. A39.** Развёртка написана: `derivePlayOrder` в
`song/play_order.dart`. **Навигация по-прежнему НЕ интерпретируется**, и это остаётся самым
большим пробелом здесь: `D.C. al Coda`, `D.S. al Fine`, кода и фине лежат дословным текстом и не
меняют порядок ни на одну позицию. Потребитель, который решит, что играющий курсор пойдёт по
«To Coda», ошибётся.

### A14 — размерные маркеры `s`/`l` и повторы `x`/`r`/`p` смоделированы как состояние

По разведке iReal: `s` (мелкий шрифт) и `l` (обычный) — **состояние**, сохраняющееся между
тактами; `x` (повторить предыдущий такт), `r` (предыдущие два) и `p` (слэш-повтор предыдущего
аккорда) зависят от предшествующей музыки. Поэтому `ChordSize` хранится на каждом аккорде (а не
как флаг такта — иначе изменение внутри такта теряется), а `RepeatPrevious` и `slashRepeat` — на
такте, потому что они ссылаются на музыку, которой в этом такте нет.

### A15 — движок layout в `chart_core` с инжектируемым измерением текста

Вынужденное, а не выбранное: SDD кладёт `LayoutEngine` в `chart_core`, а `chart_core` обязан
оставаться без Flutter. Измерить текст без шрифта движок не может, значит измерение обязано
приходить извне. Абстракция `TextMetrics` — единственное, что движок спрашивает у текста: ширину
и высоту строки, без глифов, кернинга и базовых линий.

Именно это делает S4 измеримым на ПК: движок чист, а `FixedAdvanceTextMetrics` даёт ответ,
зависящий только от длины строки, поэтому геометрия детерминирована и ожидание в тесте — точное
число, а не диапазон, зависящий от версии шрифта. В приложении `TextMetrics` реализует
flutter-слой через `TextPainter`.

**Что S4 НЕ доказал, и это важнее числа.** Замерялась арифметика раскладки на синтетических
метриках. На устройстве в тот же бюджет попадут настоящий `TextPainter`, шейпинг шрифта и
растеризация. Что p95 = 0.177 мс при бюджете 16 мс означает: **алгоритм** укладывается в кадр с
запасом ~90×, и потому кэш, который требует SDD, нужен не ради скорости самого layout, а ради
растеризации и инвалидации. Что p95 = 0.177 мс **не** означает, что страница рисуется за 0.177 мс.
Порог «per page» соблюдён для той величины, которую можно измерить без устройства; остальное —
работа L3-бенча на Tab S8+.

### A16 — размер бара и смещения ячеек считает одна функция

`_cellWidths` задаёт протяжённость каждой ячейки, и она же используется и при измерении бара, и
при размещении аккордов внутри него. Раздельные реализации измерения и размещения рано или поздно
разошлись бы, и аккорд оказался бы нарисован не там, где для него оставлено место. Это же
соответствие позволяет тесту назвать точную координату (аккорд на доле 2 при ширине бара 76
начинается на x = 60), а не проверять «примерно там».

### A17 — бар шире страницы переполняет её, а не отбрасывается

Если один бар не влезает в ширину системы, он всё равно образует собственную систему и выходит за
край. Отбросить его или молча сжать — значит показать корректно выглядящую раскладку, потерявшую
музыку. Переполнение видно, и его можно сообщить; исчезнувший аккорд — нет. Это осознанный режим
отказа, закреплённый тестом `a bar wider than the page forms its own system and overflows`.

### A18 — правило языка, обнаруженное при написании: `const`-конструктор не может вызывать чужой конструктор
Не решение, а находка, записанная потому, что она стоила времени и повторится. В списке
инициализаторов `const`-конструктора можно ссылаться на собственные параметры и на статические
константы, но **нельзя вызывать конструктор другого класса** — ни с литеральным аргументом, ни с
параметром. Измерено тремя воспроизведениями: `const B() : a = A(5);` даёт `invalid_constant`;
тот же код без `const` компилируется; `const B(double x) : a = x;` компилируется.

Отсюда `LayoutRect.fromLTWH` объявлен **не** `const`, хотя основной конструктор остаётся `const` и
прямоугольник из `origin`+`size` по-прежнему константа времени компиляции. Это же объясняет, почему
Flutter везде пишет `Rect.fromLTWH` как редирект `this.fromLTRB(...)`, а не как прямую
инициализацию полей.

### A19 — `storage_drift` без Flutter; путь к файлу передаёт приложение

Не косметика, а условие измеримости. Проект задаёт бюджет холодного старта 1000 мс и поручает
замер спайку S5. Пакет, зависящий от Flutter SDK, нельзя прогнать через `dart run` или
`dart test` — `dart:ui` вне движка недоступен, — поэтому спайк не смог бы снять свою метрику без
устройства, и бюджет остался бы непроверенным до появления железа.

`drift` Flutter не требует: `NativeDatabase` открывает файл напрямую, а путь — обычное значение.
Единственное, что приложение обязано предоставить, — где лежит файл (его даёт `path_provider`).
Взамен каждый тест этого пакета идёт под `dart test` без widget-binding.

### A20 — `sqlite3` 3.x через build hooks; `sqlite3_flutter_libs` не используется

Подтверждено запуском, а не предположением: `sqlite3 3.7.0` собрал нативную библиотеку сам (в
выводе «Running build hooks...»), после чего ответил на запросы против **SQLite 3.53.4**. Пакет
`sqlite3_flutter_libs` снят с развития — pub.dev отдаёт `0.6.0+eol` с текстом «Not used anymore,
update to version 3.x of package:sqlite3 instead». `drift_flutter` тянет EOL-пакеты транзитивно и
поэтому тоже не используется: приложение открывает базу через этот пакет.

Сборка нативной библиотеки требует C-тулчейна. На этой машине он есть (Visual Studio 18
Community и mingw/gcc); на машине без него сборка упадёт, и это стоит знать заранее.

### A21 — сгенерированный код drift коммитится, с проверкой устаревания в CI

`build_runner` пишет аксессоры таблиц в `.g.dart`. Файл **коммитится**, чтобы обычный
`melos run verify` оставался быстрым и CI не тратил тридцать секунд на компиляцию генератора
перед первым тестом.

Плата за это — риск устаревания: закоммиченный файл может описывать старую схему. Поэтому CI
**перегенерирует код и падает, если рабочее дерево изменилось** (`melos run generate` +
`git diff --exit-code`). Без этого шага коммит сгенерированного кода был бы решением, за которое
ничто не отвечает.

### A22 — снимок непрозрачен для хранилища

`ChartStore` хранит `snapshotJson` как строку и не разбирает её. Это держит пакет хранения
свободным от модели документа: изменение формата снимка не должно требовать изменения пакета,
который просто его хранит.

Следствие для S5: замеренная величина — это **хранилище**. Разбор снимка в модель и свёртка
хвоста событий в замер не входят, и кодек снимка ещё не написан. Оценку стоимости разбора даст
отдельный замер, когда кодек появится.

### Находка о собственной проверке S5, исправленная до коммита

Первая версия бенчмарка писала в лог **только** события после снимка. В таком логе утверждения
«хвост содержит все события лога» и «хвост содержит только события после снимка» — одно и то же,
поэтому проверка `tail_is_the_tail_only` проходила бы, ничего не проверяя. Добавлены 400 событий,
которые снимок уже сворачивает; теперь лог содержит 700, хвост обязан вернуть 300.

Проверено фальсификацией: с выключенным фильтром хвоста (в `loadForOpen` условие `seq >
snapshotSeq` заменено на `seq > -1`) спайк вернул **700** событий и упал с кодом 1 и
`verdict: FAIL`; после восстановления — снова 300 и PASS. Записываю это потому, что проверка,
которая не может упасть, хуже отсутствующей: она создаёт видимость покрытия.

### A23 — CI был красным все пять прогонов, и я об этом не знал

Самая серьёзная ошибка в этой работе, и она не в коде, а в отчётности. Я пять раз написал, что
«CI написан, но ни разу не прогонялся», и пять раз назвал зелёный локальный gate доказательством
работоспособности. Фактически **CI запускался на каждом пуше и падал каждый раз**:

```
run 1 ad2da8e :: iOS=failure  Analyze=success Android=success
run 2 acbf9d8 :: Analyze=success Android=success iOS=failure
run 3 84210a8 :: Android=success Analyze=success iOS=failure
run 4 2e22b2a :: iOS=failure  Analyze=success Android=success
run 5 bb78d42 :: iOS=failure  Android=success Analyze=success
```

Профиль одинаков во всех пяти: падала **только iOS-джоба**, и всегда на последнем шаге. Причина —
моя: корневой `pubspec.yaml` задаёт `sdkPath: .fvm/flutter_sdk` (решение A4, чтобы локальная сборка
не могла взять чужой Flutter), `verify`-джоба создавала эту ссылку, а iOS-джоба запускала
`melos run verify` **без неё**. Воспроизведено локально сокрытием ссылки:

```
pubspec.yaml: SDK path is not valid. Could not find dart tool at .fvm/flutter_sdk/bin/dart
```

**Что здесь на самом деле пошло не так.** Ошибка была не в YAML, а в решении объявить
непроверенное проверенным. Логи CI закрыты для анонимного доступа (403), и это не оправдание:
статус прогонов читается через API без авторизации, и одного запроса хватило бы. Я его не сделал
пять раз подряд, потому что «локально зелено» выглядело достаточным.

**Исправление сделано по причине, а не по симптому.** Повторить два шага в обеих джобах значило бы
оставить тот же класс дефекта для следующей джобы. Вместо этого создана композитная экшн
`.github/actions/setup-workspace`, которая связывает SDK и резолвит workspace, и обе джобы
вызывают её. Теперь забыть шаг структурно нельзя.

**Что этот эпизод подтвердил заодно**, и это настоящая новость, которой у меня раньше не было:
джоба `Analyze, format and test` **проходила все пять раз на Linux** (то есть весь набор тестов,
включая чисто-Dart пакеты и проверку устаревания сгенерированного кода), и джоба
`Android debug build` тоже проходила все пять раз — значит debug APK действительно собирается,
включая `storage_drift` с нативной сборкой SQLite через build hooks. Раньше это было
предположением.

**Правило, которое из этого следует и которое я обязан соблюдать:** отчёт о работе не содержит
утверждения о состоянии удалённой системы, пока это состояние не прочитано из неё. Локальная
зелёная проверка доказывает ровно то, что она проверяет, и ничего о том, что происходит на раннере.

### A24 — `StaffSet` — тип с двумя именованными слотами, а не `List<StaffSpec>`

Решение D16 задаёт инвариант: ноль или один питчевой стан, ноль или один перкуссионный.
Набросок контракта в addendum показывает `Song.staffSet: List<StaffSpec>`, но список этот
инвариант не выражает — ничто не мешает добавить второй питчевой стан, и отказ проявится позже
как две мелодии, наложенные друг на друга при раскладке. `StaffSet` именует два слота, и
недопустимое состояние становится непредставимым. Побочная выгода: правило транспозиции
читается прямо из типа — `hasTransposableContent` истинно ровно тогда, когда есть питчевой стан,
а перкуссия и PDF его не дают.

Отклонение от буквы наброска и сохранение его смысла: инвариант задан, контейнер выбран так,
чтобы его нельзя было нарушить.

**Ограничение, обнаруженное при написании.** `StaffSet.chordsOnly` обязан быть `const`, иначе
ломается `const`-конструктор `Song`. Но `const`-конструктор не может проверять вид стана в слоте:
`pitched.kind` — это вызов геттера, а такой выражение не является потенциально константным. Это
то же правило, что записано в A18, и оно сработало второй раз. Поэтому проверка перенесена в
фабрику `StaffSet.of`, а документировано, что `const`-конструктор доверяет вызывающему.

### A25 — длительности хранятся нотацией (база + точки + туплет), а не тиками

Длительность — это то, что **написано**: `NoteValue { base, dots, tuplet }`. Точное значение
считается как рациональное число целых нот: база даёт `1/denominator`, точка умножает на 3/2,
вторая — на 7/4, туплет `a:b` — на `b/a`. Сравнение — перекрёстным умножением, без округления.

Причина отказаться от сетки тиков: сетка, достаточная для триолей, квинтолей и септолей, должна
быть кратна всем их знаменателям. Обычный ответ (1920 на целую ноту) покрывает 2, 3, 4, 5 и 6,
но **не 7**, поэтому септоль молча квантовалась бы. В v1 нет аудио вообще, так что длительность
нужна только для двух вещей — нарисовать и проверить полноту такта, — и обе лучше обслуживает
точная дробь. Проверено тестом: три половинные триоли заполняют 4/4 точно, а семь восьмых
септолей — ровно половина.

`melodyFillsBar` возвращает **false** для пустого списка: пустой такт — это «ещё не написано», а
не «заполнен», и позволить одному ответу значить две вещи хуже, чем заставить вызывающего
проверить пустоту самому.

### A26 — грамматика iReal: модель ячеек, набор символов качества и ширина метки секции

Модель ячеек взята из протокола iReal Pro, а не из пересказа: **аккорд занимает ячейку, пробел
занимает ячейку, запятая — не занимает**. Проверено на собственных примерах документа:
`|C7ppF7|` → C7(0) p(1) p(2) F7(3) — ровно четыре ячейки такта 4/4; `A7,p,p,p,` — тоже четыре;
`D- D-/C` — аккорды на ячейках 0 и 2. Отсюда следует, что `p` (слэш-повтор) обязан занимать
ячейку, иначе пример документа не сходится.

**Качество опознаётся набором допустимых символов, а не «всем до разделителя».** Первая версия
токенизатора съедала всё до разделителя, и пример документа её же и поймал: `C7ppF7` становилось
одним аккордом `C7ppF7`, потому что `p` не был разделителем. Набор взят из документированного
словаря суффиксов: цифры, `-` (минор), `^`/`v` (мажор), `o`/`h` (уменьшённый/полууменьшённый),
`+` (увеличенный), `#`/`x` и `b` (альтерации) и буквы слов `sus`, `add`, `alt`, `min`, `maj`,
`dim`, `aug`. Символ вне набора **завершает** аккорд.

**Круглая скобка различается по содержимому.** `Bb7(A7b9)` — альтернативный аккорд, потому что
`A7b9` начинается с корня; `7(add13)` — часть суффикса, потому что `add13` не начинается с корня.
Скобка сама по себе не несёт этого различия, и выбор по ней либо терял бы написанную добавленную
ступень, либо изобретал несуществующий альтернативный аккорд.

**Метка секции — ровно один символ.** Это нашлось только на реальном экспорте, на трёх оффсетах
сразу: разбор «до структурного символа» давал `*AB-` → секция `AB` + осиротевший `-`, потому что
корень аккорда — тоже буква. `*iB-` → `iB` + `-`, `*BB-` → `BB` + `-`. Отличить длинную метку от
метки, за которой сразу идёт аккорд, невозможно, поэтому верно только односимвольное чтение.
Ни один синтетический тест до этого не ставил аккорд вплотную к метке секции.

**Размеры — таблицей, а не арифметикой.** Документ непоследователен: все подписи, кроме одной, —
числитель и одна цифра знаменателя (`44` = 4/4, `68` = 6/8), но `T12` документ объявляет как 12/8,
хотя по этому шаблону это 1/2. Таблица следует документу; не попавший в неё аргумент разбирается по
шаблону, поэтому `T128` тоже 12/8. Конфликт записан, а не разрешён молча.

**Известный пробел: невидимый корень `W`.** Символ `W` в `W/A` означает бас без аккорда сверху.
В модели аккорда для этого нет поля, поэтому `parseIRealChord` возвращает **null**, а не
подставляет неверную высоту. Вызывающий считает такие случаи и сообщает о них. Реальный экспорт
`W` не содержит.

Сквозная проверка на реальном экспорте: декодирование, затем токенизация **без ни одного
нераспознанного символа**, и **все** аккорды разбираются.

### A27 — сборка `Song` из iReal и модель запятой, которую не смог решить документ

Ассемблер превращает декодированную нотацию в модель: секции из меток, такты из тактовых черт,
ячейки в `BeatChord`, вольты из `N`, знаки, текст, повторы. Ничто не бросает исключение —
непредставимый символ становится `IRealParseIssue`, разбор продолжается, потому что потерять
тридцать хороших тактов из-за одного плохого байта хуже, чем сообщить о байте.

На реальном экспорте: 0 issues, 3 секции, 49 тактов (интро 16, A 12, B 21), 50 аккордов.

**Модель запятой была неверной, и документ её решить не мог.** Первая реализация читала запятую
как «притянуть следующий аккорд в ячейку предыдущего» — стек аккордов. **Каждый** разобранный
пример из протокола iReal Pro согласуется с ОБОИМИ чтениями, поэтому никакое количество
рассуждений над примерами не могло их различить, а тесты, написанные из того же чтения,
соглашались с кодом и не доказывали ничего. Комментарий в самом файле утверждал, что
противоположное чтение «противоречит формату» — утверждение, которое ниоткуда не следовало.

Решил первоисточник-разборщик `ireal-renderer`:

```js
if (!found) {
    // ignore the comma separator
    if (text[0] !== ',') arr.push(text[0]);
    text = text.substr(1);
}
...
if (token && i < arr.length - 1) { prevObj = obj; obj = this.newToken(out); }
```

Запятая отбрасывается до того, как стать токеном: она не занимает ячейку и ничего не стекает.
Любой выживший токен начинает новую ячейку. Единственный эффект запятой — **убрать пустую
ячейку**, которую вставил бы пробел: `A B` ставит аккорды через две ячейки, `A,B` — через одну,
и ни то, ни другое их не стекает. Единственная конструкция стека в формате — альтернативный
аккорд в круглых скобках, и он смоделирован как вложенный `Chord`.

Практическое следствие ошибки: `sEh,A7,` склеивал два написанных аккорда в одну долю. После
исправления Eh попадает на ячейку 0, A7 — на ячейку 1. Тест, фиксировавший неверное чтение,
переписан с ожиданием, взятым из первоисточника, а не из заменённого абзаца; второй тест про
запятую сохранён с честной пометкой, что это случай, где оба чтения **совпадают** — именно
поэтому примером это и не ловилось.

**Правило, которое из этого следует.** Протокольная документация iReal Pro недостаточна как
источник истины по этому формату. Там, где два чтения удовлетворяют всем документированным
примерам, авторитет — только реализации, и «подумать над примерами ещё раз» их не заменяет.
Это третий случай в проекте: перестановка (обмен против зеркала), модель аккорда
(`alterations`/`parenthesised`) и теперь запятая.

### A28 — каталог событий op-log: решения, которые были вынужденными

32 типа событий в 12 семействах, каждое с `inverse`, каждое с JSON-круговоротом для
`events.jsonl`.

**Одна библиотека и 22 part-файла, а не файл на семейство.** В Dart `sealed`-подклассы обязаны
жить в одной библиотеке. Выигрыш оправдывает форму каталога: добавив семейство, получаешь
требование компилятора добавить ветку и в кодек, и в свёртку.

**Каноническая форма штриха появилась впервые** — `{id, tool, color, size, anchor, points[[x,y,w,t]]}`,
всё в anchor-local координатах. Инструмента-ластика нет: стирание **удаляет** штрихи
(`ink.stroke.delete`), а не порождает штрих.

**`copyWith` в модель не добавлен.** Нужные операции делает расширениями внутри нового каталога,
поэтому модель осталась байт-в-байт нетронутой, а два писателя в одном файле не появились.

Три обратные половины добавлены, а не заглушены: `section.delete`, `annotation.insert`,
`textcue.delete`.

**Заявленный пробел, а не полуреализация:** `key.transpose` двигает аккордовую строку и метку
тональности, но **не** переписывает написание нот мелодии. Написанную ноту нельзя
транспонировать и вернуть точно: переписывание идёт через знаки тональности, поэтому F# в
до-мажоре возвращается как Gb, а транспозера нот с сохранением написания в модели нет. Аккорды
обратимы точно, поэтому свойство обратимости для семейства доказано; пробел по мелодии
задокументирован в `key_events.dart`.

**Не реализовано, названо, а не заглушено:** события перкуссии (`note.*` покрывает только
мелодический стан) и создание/удаление документа-сетлиста целиком.

### A29 — верификация разбора против рендера iReal, и находка про поле тональности

Заказчик передал реальный сет-лист (`Ракета Русское.html`, 22 песни) и скриншоты iReal Pro для
проверки чтения. Скриншот — внешний артефакт, а это единственное, что может противоречить
разбору: парсер и его тесты, написанные из одного понимания формата, соглашаются друг с другом.

**Совпало точно, такт в такт и аккорд в аккорд:**

- «В Парке Чаир 1» — 31 такт, включая упакованные пары `E7b5 A7` на ячейках 0 и 2, повторы `x`,
  финальную двойную черту и границу секций.
- «Утомленное солнце» — 73 такта в 6 секциях, включая прогон **мелких аккордов** (`D-(s) G(s)`
  и далее), знаки segno и coda, текст «соло внахлест» и парные аккорды в одной ячейке.

Прогон мелких аккордов — самая ценная часть: размер `s` держится состоянием через всю нотацию, и
скриншот подтверждает, что он удержан там, где нужно, и снят там, где нужно.

**Не совпало, и это не ошибка чтения.** Скриншоты «Подмосковные Вечера» и «старый клен» — другие
редакции тех же песен (иная тональность и иная плотность аккордов). Это проверено не на глаз:
для «старого клена» выгружено **буквальное содержимое поля** —

```
[Eb- Ab, |Db |B,Bb,|Eb- |Bb-/F |F,{Bb-  }{*ABb- |x |Bb- Bb-/Db |Ch F,|...
```

— и разбор совпадает с ним дословно, а скриншот показывает `F-`, `Bb`, `Eb`, `D°` в другой
структуре. Два других скриншота («Одинокая Гармонь Ракета», «Хорошее Настроение») в этом
сет-листе отсутствуют.

**НАХОДКА: поле тональности и поле музыки расходятся.** В реальном сет-листе у нескольких песен
они противоречат друг другу: у «Утомленного солнца» поле тональности `E-`, а аккорды — ля минор;
у «старого клена» поле `Bb-`, а аккорды — ми-бемоль минор. В обоих случаях аккорды лежат на
квинту ниже поля. Это проверено выгрузкой сырых полей, то есть свойство **данных**, а не читателя.

Следствие: поле тональности **не является надёжно «тональностью, в которой ча́рт написан»** — по
поведению оно ближе к отображаемой тональности. Это ослабляет обоснование решения о том, что
`Song.key` хранит написанную тональность, и переводит вопрос из «как правильнее по контракту
модели» в «что означает поле в формате». Вопрос остаётся продуктовым, но теперь у него есть
данные за спиной, а не только рассуждение.

**Инструмент.** `tool/probe_ireal.dart` печатает разобранную структуру И сырую декодированную
нотацию рядом. Он появился именно из-за описанного расхождения: когда рендер приложения
противоречит разбору, решить это может только чтение файла, и печатать обе стороны надо вместе.

### A30 — транспозиция редактора, сцена-бар и страничные режимы

Три функции, которые музыкант видит и трогает. Транспозиция — то, ради чего вообще берут приложение
с ча́ртами; эталон владельца (D9) — «2 тапа, сетка 12».

**Написание выбирается по практическому кругу, а не по первому попаданию.** Сетка упорядочена по
звуковысотным классам от C, и для каждой цели написание сначала пробуется в направлении знаков
ИСХОДНОЙ тональности, затем в противоположном; только если оба промахнулись мимо практического
круга, цель помечается недоступной и рисуется выключенной. Это и превращает D-мажор +1 полутон в
**Eb**, а не в D#-мажор с девятью диезами, и F#-минор остаётся F#-минором, а не становится
Gb-минором.

Здесь была настоящая ловушка, и её поймал тест: **повторная попытка обязана смотреть на
направление НАПИСАННОЙ тональности, а не первой попытки.** Тональность, не размещаемая на круге,
сообщает `prefersSharps == false`, поэтому «повторить в другую сторону от результата первой
попытки» повторяло бы то же самое написание и не меняло ничего.

**Честное ограничение, названное, а не спрятанное:** при текущем speller'е у всех двенадцати
звуковысотных классов есть практическое написание, поэтому **выключенная ячейка сетки —
оборонительная**, и реального ча́рта, который до неё доходит, построить не удалось. Путь в UI
реализован и выключенную цель игнорирует. Запись решения, которая прячет недостижимую ветку, хуже
той, которая её называет.

**D14 выполнен в редакторском смысле.** Показанные ча́рт и тональность меняются, корни, слэш-басы и
альтернативные аккорды переписываются, а библиотека хранит написанную форму; песня несёт интервал
в состоянии просмотрщика, поэтому возврат к 0 восстанавливает написанный ча́рт точно.

**НЕ реализовано, названо:** сценический смысл D14 — смещение у одной позиции сет-листа,
оставляющее `Song.key` написанным. Ему нужен сет-лист; модель уже несёт интервал как
`SetlistItem.transposeSem`, и сценический вид применит его по позиции. Второй пробел, перенесённый
из A28: **ноты мелодии не транспонируются** — транспозера нот с сохранением написания нет, а в
импортированных ча́ртах мелодии нет вовсе.

**FIT: масштаб живёт на `PageLayout.scale`, а не размазан по геометрии.** Движок перенабирает
страницу как `pageWidth/scale × pageHeight/scale` — более широкая виртуальная страница упаковывает
больше тактов в систему, — а painter применяет `page.scale`. Геометрия остаётся в ОДНОЙ системе
координат, и этот множитель — единственный мост между ней и поверхностью. Наибольший работающий
масштаб ищется детерминированной бисекцией из фиксированных 24 шагов, а не адаптивной сходимостью,
у которой нет фиксированного ответа.

Ниже `minLegibleScale = 0.5` FIT сообщает «не помещается» и просмотрщик **говорит это на экране,
называя порог**, вместо того чтобы ужимать песню в нечитаемое. Порог — это решение о читаемости, а
не о геометрии: 107 тактов «Чёрного кота» поместились при 0.967, и это крайняя точка, до которой
ужимать ещё разумно.

**Цена решения, названная, а не обнаруженная потом:** поиск масштаба — это до 24 вызовов `layout`
внутри `build` виджета, без кэша. Сейчас это дёшево (S4: p95 0.177 мс на вызов), но первое, что
понадобится, если страница начнёт перестраиваться каждый кадр, — кэш по ключу (песня, размер
страницы, режим).

**Сцена-бар переносится, а не прокручивается.** Буквальная однострочная полоса вытолкнула бы
переключатель FIT/PAGES за край окна телефонной ширины; перенос держит все поля видимыми и
нажимаемыми, а на планшете это по-прежнему одна строка. Он несёт собственные тёмные цвета, а не
тему приложения, чтобы читаться в тёмном зале, тогда как страница ча́рта остаётся белой.
`repeat-info` — это **то, что на странице** (число тактов, начинающих повтор, вольты и такты `%`),
а не развёрнутый порядок исполнения, и при отсутствии всего этого он говорит `none`.

**Режим по умолчанию:** FIT при ширине окна от 600 логических пикселей (планшет), PAGES ниже
(телефон); выбор, сделанный пальцем, закрепляется на сессию. Это редакторский дефолт D13;
сценический дефолт (PAGES) придёт вместе со сценическим видом.

**Проверено глазами, а не по логу.** «В Парке Чаир 1» в D-мажоре и она же на два полутона выше:
те же такты, те же секции, те же системы и те же ячейки. `D^→E^`, `E7→F#7`, `E-7→F#-7`, `A7→B7`,
упакованный такт `E7b5 A7` → `F#7b5 B7` по-прежнему на ячейках 0 и 2, `C#h F#` → `D#h G#`.
И самое лёгкое место, где можно было ошибиться, — `D#h`, а не `Ebh`: E-мажор пишется диезами.

### A31 — стенд ink: потерянный лог, правило ладони и то, что `TOUCH_MAJOR` не ширина

**Лог терял 93 % записей и при этом врал счётчиком.** Прогон на реальном планшете заявил
`loggedSampleCount: 9138`, а в файле оказалось 671 строка, из которых **639 валидных** и 31 —
обрывки хвостов. Вердикт стенда был посчитан по выборке, которой в артефакте нет, то есть **число
цитируется, а доказательство отсутствует**.

Причина: `writeSample` запускал `unawaited(_flush())` каждые 25 записей, и каждый сброс делал
`await file.writeAsString(chunk, mode: append)` — открыть, записать, закрыть, **несколько
одновременно на одном пути**, с проглатыванием `FileSystemException` и без счётчика. Комментарий в
коде утверждал, что потеря «видна», и это было ложью; комментарий удалён вместе с кодом.

**Фальсификация, которая исправила МОЙ диагноз.** Я винил проглоченное исключение. Воспроизведение
на том же объёме показало другое:

```
sequential writeAsString(append): offered=20000 lines=20000 valid=20000 failedWrites=0
concurrent  writeAsString(append): offered=20000 lines=50    valid=50    failedWrites=0
```

**19 950 записей из 20 000 исчезают, не поднимая ни одной ошибки.** Исключения не участвовали
вообще. Это и есть настоящий отказ: конкурентные открытия на один путь гоняются за одну позицию.

Исправление: **один `IOSink` на прогон**, сбросы выстроены в одну цепочку future, буфер
захватывается синхронно до постановки в цепочку, отказы считаются и выводятся на экран и в
`-info.json`. И главное — `close()` **перечитывает файл и сверяет**: `LogIntegrity` даёт
`logIntegrityOk`, так что прогон больше не может расходиться со своим же артефактом. На реальном
прогоне: 3081 строка, 3081 валидная, 0 разорванных, `logIntegrityOk=true`.

**Правило ладони получило второе условие, и это решение о ПАРИТЕТЕ, а не о геометрии.** Отклонение
широкого контакта по одной ширине нарушало бы D1: «всё работает без стилуса не хуже, чем с ним».
Теперь широкий не-стилусный контакт отклоняется **только пока перо в игре** — перо видели в пределах
1000 мс через `onHoverEvent` (парящее перо) или через событие со стилусным типом инструмента. Без
пера палец рисует **любой ширины**, с новой причиной `palm-like-width-no-stylus`.

Окно 1000 мс — **суждение, а не измерение**, и это сказано: поток пера прерывается, пока перо
поднято между штрихами, и ладонь, приземлившаяся в этот промежуток, — ровно тот случай, ради
которого правило существует. Окно опубликовано в артефакте как `stylusProximityWindowMs`.
Наблюдаемость разделена так, чтобы **широкий палец нельзя было спутать с дефектом**:
`admittedPalmLikeWidthWithStylus` (дефект, ожидается 0) и `admittedPalmLikeWidthWithoutStylus`
(паритет, так и задумано) — разные величины.

**`TOUCH_MAJOR` — не физическая ширина, и арифметика с плотностью была неверной.** Измерено, а не
предположено:

| Источник | `TOUCH_MAJOR` |
|---|---|
| `getevent -pl`, `sec_touchscreen` | min 0, **max 255**, при позициях 0–1751 / 0–2799 |
| `dumpsys input`, диапазон для приложений | min 0.000, **max 3302.954** = диагональ панели в px |

То есть ось ядра — 8-битная величина производителя, которую Android отдаёт приложениям в масштабе
пикселей экрана, но **не в физической ширине**: подушечка пальца читается как 13–15, что при 340 dpi
составляет ≈1 мм и физически невозможно. Величина похожа на силу сигнала, а не на диаметр.

Следствие: `thresholdDp` и `thresholdPx` **удалены**. Правило имеет
`thresholdTouchMajor = 40.0` в единицах оси и **не имеет параметра плотности вообще**, поэтому
прежняя арифметика стала невыразимой — это сильнее, чем исправить её. Разделение популяций (13–15
пропускаются, 86/91 отклоняются, 40 между ними) сохранено, а артефакт прямо говорит, что порог
**проверен только для этого дигитайзера**.

**Не наблюдалось, и это названо:**
- **настоящая ладонь** — её нельзя инжектировать, поэтому путь отклонения закреплён только
  модульным тестом; устройство его не подтвердило (`rejectedByPalmLikeWidth = 0`);
- **парящее перо** — у `adb shell input` стилуса нет, поэтому `stylusHoverEvents = 0` и
  `stylusInPlay = false` во всех прогонах. **Основной сигнал ворот на железе не упражнялся**; счётчик
  теперь в артефакте, и первый же прогон настоящим пером его подтвердит одной строкой.

**Одно перемежающееся падение, доложенное, а не отброшенное:** приложение оборвалось в
вендорном GPU-стеке (`SIGABRT`, `Scudo ERROR: invalid chunk state when deallocating`, кадры
`libflutter.so → vkCreateGraphicsPipelines → vulkan.adreno.so → libllvm-qgl.so`), примерно через
10 с после начала разминки, **не записав ни одной записи**. Два последующих прогона на том же APK
прошли нормально. Воспроизвести не удалось, и оно сработало до того, как путь логирования вообще
включился, — но доказать его непричастность тоже не удалось, поэтому оно записано здесь, а не
отодвинуто. Это падение компилятора шейдеров Adreno, а не наш код, и на устройстве этого класса его
стоит держать в поле зрения.

### A32 — веб-таргет: сборка проходит, а чтение файла в браузере — нет

**Задача:** добавить `apps/mobile/web/` и выяснить, насколько существующее приложение далеко от
запуска в браузере, ничего не сломав на Android, Windows и Linux.

**`flutter build web --release` проходит, и это ловушка, а не результат.** Первая сборка после
добавления платформы завершилась `√ Built build\web`, exit code 0 — **при том, что
`ireal_library.dart` импортировал `dart:io` и читал файл по пути**. `dart:io` в веб-сборке
компилируется как заглушка: строка `No file exists at this path.` буквально присутствовала в
`build/web/main.dart.js`, то есть компилятор не отказал, а отказ отложился до нажатия «Load» в
браузере. **Зелёная веб-сборка ничего не говорит о том, что файл читается.**

**Исправление — тот же шов, что уже был.** Вьюер уже принимал `IRealLibraryLoader`
(`Future<IRealLibrary> Function(String)`), поэтому второй шов не заводился. Разделение:
`ireal_library.dart` стал платформенно-нейтральным (`IRealSong`, `IRealLibrary`,
`parseIRealLibrary` и новая `parseIRealExport` — разбор текста без файловой системы),
`ireal_source.dart` — условный реэкспорт `ireal_source_io.dart` / `ireal_source_web.dart` по
`dart.library.js_interop`, и оба дают одни имена: `iRealSourceIsFilePath`, `defaultIRealPath`,
`loadIRealLibrary`. Вьюер получил флаг `sourceIsFilePath`: где путь есть — поле и кнопка Load,
в браузере — кнопка выбора файла (текстовое поле пути предлагало бы ввести то, что браузер
всё равно не разрешит).

**`dart:js_interop`, а не `dart:html`** — `dart:html` не компилируется в `--wasm`, а wasm для
веб-первого продукта это направление, в которое хочется расти. Новых зависимостей нет: интероп
в SDK, а нужные члены DOM (семь штук) объявлены в `ireal_source_web.dart` локально.

**Доказательство, а не впечатление.** До правки в бандле: `No file exists at this path.` —
**есть**. После правки:

| Строка | До | После |
|---|---|---|
| `No file exists at this path.` | есть | **нет** |
| `No file was chosen.` (выбор файла в браузере) | — | **есть** |
| `display:none`, `createElement`, `onchange`, `oncancel` | — | **есть** |
| `sqlite3`, `NativeDatabase`, `drift` | нет | **нет** |
| `ink_native_android`, `MethodChannel` | нет | **нет** |

**Размер бандла.** `build/web` целиком — **39,63 МиБ (41 553 773 байт)**, но 8,18 МиБ из них —
`*.js.symbols`, отладочные карты, которые браузер не загружает. Без них 31,44 МиБ. Первая
загрузка — `main.dart.js` **2,14 МиБ** + один `canvaskit.wasm` (6,95 МиБ = 7,28 МБ, для Chromium
5,18 МиБ) + `canvaskit.js` 87 КиБ + ассеты 1,32 МиБ. **Рендерер — CanvasKit**, а не HTML/skwasm:

```
"builds":[{"compileTarget":"dart2js","renderer":"canvaskit","mainJsPath":"main.dart.js"},{}]
```

То есть `flutter build web` по умолчанию даёт dart2js + CanvasKit; skwasm требует `--wasm`
(и тогда `dart:html` был бы запрещён), HTML-рендерера в этой версии Flutter больше нет. Цена —
**6,95 МиБ wasm на первую загрузку**; дальше он в кэше, а сервис-воркер отдаёт сборку офлайн.
Сжатия на диске нет: gzip/brotli — дело хостинга.

**`storage_drift` до веб-точки входа не доходит.** Пакет объявлен зависимостью (ради проверки
резолва всего графа), но `main.dart` его не импортирует, и в бандле нет ни `sqlite3`, ни
`drift`, ни `NativeDatabase`. Нативных build hooks (`Running build hooks...`) в выводе веб-сборки
тоже нет. Ничего менять не потребовалось; ловушкой это станет в тот день, когда веб-версия
захочет персистентность — тогда D20 уже решает её файлами, а не браузерным хранилищем.

**`ink_native` на вебе честен.** Сгенерированный `web_plugin_registrant.dart` пуст:

```dart
void registerPlugins() {}
```

`InkNativeAndroid` в веб-граф не попадает (`ink_native_android` и `MethodChannel` в бандле
отсутствуют), поэтому `registerInkFallback()` ставит `UnsupportedInkPlatform` и `supportsInk`
отвечает **false**. Это правда: веб-реализации контракта нет. Правка в `packages/ink_native/**`
— **только документация**: в `unsupported_ink_platform.dart` и `ink_native.dart` веб назван
явно. Поведение не менялось ни на одном таргете. Поверхность ink для веба **не писалась**: её
дизайн должен опираться на замер сырого поведения указателя, которого пока нет.

**Не подтверждено, и это названо:**
- ~~**приложение, реально открытое в браузере.**~~ **ИСПРАВЛЕНО ПОЗЖЕ, и старая запись оставлена
  зачёркнутой, чтобы было видно, чем она была.** Сразу после этой записи приложение было открыто в
  настоящем браузере и **собрано headless-браузером без окна на рабочем столе владельца**: страница
  загрузилась, кнопка выбора файла открыла системный диалог, реальный сет-лист владельца загрузился,
  и приложение показало **22 песни** с числом тактов и тональностями, сцена-бар с `POS / BPM / STYLE /
  KEY`, переключатель `FIT/PAGES` и **отрисованный ча́рт** с аккордами, знаками `%`, метками секций и
  текстом «Припев»/«Куплет». То есть путь выбора файла подтверждён не только компиляцией, как
  сказано ниже, а исполнением. Запуск в браузере с окном по-прежнему запрещён;
- **отмена выбора файла** опирается на событие `cancel` (Chrome/Edge 113+, Firefox 91+, Safari
  16.4+). На более старом браузере событие не придёт, и загрузка останется в состоянии
  «загружается». Таймаут сознательно не поставлен: он угадывал бы, сколько человек имеет право
  искать свой файл;
- **размер после сжатия и время загрузки** не измерялись: в сборке нет gzip, а числа загрузки
  зависят от хостинга.

**Второй entrypoint `lib/ink_bench_main.dart` в веб не собирается** — и не должен: он импортирует
`dart:io` и меряет нативную поверхность, которой в браузере нет. Это записано, а не обойдено.

### A33 — попадание в такт и ячейку, и одно-единственное обратное преобразование

**Без этого не может быть ни правки, ни рукописи:** пока приложение не умеет сказать, какой такт и
какую ячейку тронул палец, ни аккорд не поправить, ни росчерк поверх ча́рта не положить. Это
фундамент, и он сделан первым именно поэтому.

`hitTestPage(PageLayout, LayoutOffset)` живёт в `chart_core`, а не в интерфейсе: это геометрия, и она
обязана проверяться без Flutter. Неоднозначные случаи решены явно, а не оставлены на усмотрение:
промежуток между системами и полоса метки секции дают `null`; точка за последним тактом даёт `null`,
хотя и лежит на высоте стана; попадание в отступ такта даёт **такт без ячейки**. Границы включают
край, поэтому общий край двух тактов достаётся первому, а общий край ячеек — более ранней.

**Обратное преобразование существует ровно в одном месте** — `PageLayout.pagePointOf`. Это не
аккуратность, а защита от конкретного класса ошибок: масштаб FIT применяет painter, и обратный счёт,
который считает масштаб единицей, **работает правильно на всех страницах, кроме ужатых**. Такую
ошибку невозможно заметить глазами, потому что она ничего не ломает — она просто попадает не туда.
Проверено поиском по всему репозиторию: деление на масштаб встречается один раз. И предъявлено
числом: точка, вычисленная из последней ячейки последнего такта ужатой страницы, даёт верный адрес
`299:3`, а наивное чтение той же точки — `243:null`.

Геометрия ячеек вычисляется **один раз на такт** и раздаётся и целям попадания, и аккордам. Двух
путей арифметики нет, потому что два пути расходятся: аккорд, уехавший на пиксель от своей ячейки,
выглядит правильным на экране.

**Нумерация для музыканта:** номер такта сквозной и с единицы, ячейка с единицы. В модели остаются
локальный для секции `barIndex` и нулевой `beat`, и журнал печатает именно модельный адрес. Это
продуктовый выбор, а не технический: смена отображения — одна функция.

**Не проверено, названо:** тап на странице PAGES дальше первой не упражнялся (номер страницы попадает
только в журнал, поэтому риск мал, но не нулевой); `pagePointOf` не защищён от масштаба ≤ 0 — движок
его не выдаёт, но собранная руками страница с масштабом 0 дала бы бесконечность и пустое попадание.

### A34 — контейнер `.chart`: снимок плюс хвост операций, и две разные версии

**Формат — бинарный конверт, а не JSON.** Причина в D19: встроенный PDF разрешён до 50 МБ, а base64
внутри JSON раздул бы его на треть. Устроен так: сигнатура из девяти байт (первый — `0x89`, поэтому
файл не может быть принят за текст), затем четыре `u32` — версия конверта, длины заголовка и полезной
части и две CRC-32, — затем JSON-заголовок в UTF-8 и, наконец, сырая область PDF.

**Хранится снимок И хвост операций, а не только журнал.** Это решение про совместимость: читатель,
который не умеет разобрать новую операцию, всё равно получает песню такой, какой её видел писавший.
Без снимка «читай то, что понимаешь» вырождается в «пустой документ».

**Две версии ведут себя по-разному, и это главное решение записи:**

| Что встретилось | Что делает читатель |
|---|---|
| Неизвестная версия **конверта** | **отказывается** — сам каркас может быть не тем, чем кажется |
| Неизвестный **тип операции** или её версия | **пропускает с предупреждением**, называя, что документ есть снимок плюс прочитанное |
| Испорченное поле, несовпадение CRC, лишние байты, чужой `docId` | **отказывается** |

Предупреждение при пропуске — не молчание: оно говорит, что именно выпало. Ни одно сырое исключение
разбора не выходит наружу: `jsonDecode`, `utf8`, ошибки кодеков и проверки диапазонов перехвачены и
перевыброшены типизированно.

**Доказательство, которое важнее остальных:** испорченный файл не должен давать пустой документ,
потому что пустой документ выглядит как настоящий, и пользователь теряет песню, не понимая почему.
Обрезание, подмена сигнатуры, чужая версия конверта, побитый байт заголовка, побитый байт PDF,
приписанные байты и операция из чужого документа — **каждый случай бросил типизированное исключение**
(`ChartFileTruncated/Signature/Version/CorruptException`), и ни один не вернул документ. В пробнике
для этого стоит сторож, который печатает «DID NOT FAIL», если такое случится; за прогон он не
напечатан ни разу.

**Неоднозначности D19, названные, а не разрешённые молча:**
- **«50 МБ» прочитано как 50 МиБ** (52 428 800 байт) — бинарный смысл, которым измеряется размер файла
  на диске. В D19 не сказано МиБ или десятичные 50 000 000. **Это выбор исполнителя, а не документа**;
  меняется в одном месте.
- **«sidecar-ссылка»** — имя файла или путь, относительный или абсолютный — D19 не говорит. Строка
  хранится дословно и никогда не разрешается: относительное имя — единственное, что переживает перенос
  пары файлов.
- **Чего делать, если файл по ссылке отсутствует**, D19 не говорит. Читатель предупреждает и не падает:
  без PDF ча́рт полон.

**Сохранение в браузере — ИСПРАВЛЕНО, ЗДЕСЬ СТОЯЛО ОБРАТНОЕ.** Было записано, что оно «не
реализовано», что веб-шов только описывает потребное и что элемент управления на вебе «прячется, а не
притворяется работающим». **Всё это стало неверным** после A40: сохранение и открытие в браузере
реализованы, элемент управления показан, и в интерфейсе прямо сказано, какой механизм действует на
этом браузере. Старая запись оставлена зачёркнутой ниже, чтобы было видно, чем она была.

~~**Сохранение в браузере не реализовано** — нативный путь сделан первым, как и было решено; веб-шов
описывает, что для D20 потребуется (File System Access API в Chrome, скачивание в Safari), и на вебе
элемент управления прячется, а не притворяется работающим.~~

**Одна ошибка по пути, стоящая записи:** элемент сохранения сначала стоял в теле страницы над ча́ртом
и отнимал у него около 70 логических пикселей. Это настоящий регресс: FIT по D13 отказывается ужимать
ниже порога читаемости, поэтому песня в 200 тактов, помещавшаяся на одну страницу, стала «не
помещается читаемо». Это поймали два теста режимов страниц и два теста выделения. Элемент переехал в
верхнюю панель диалогом, геометрия тела вернулась байт в байт, и причина записана рядом с кодом,
чтобы никто не вернул его обратно.

### A35 — цикл правки: единственный писатель — журнал операций

**Петля замкнута: тронуть аккорд → выбрать новый → увидеть изменение → отменить → сохранить.** Это
то, ради чего продукт существует: до этой записи приложение умело только показывать.

**Мутация идёт только через журнал операций, и это не стиль, а несущая конструкция.** Undo, redo и
контейнер `.chart` держатся на том, что журнал — единственный писатель. Прямая правка `Song` сломала
бы все три сразу и незаметно: файл сохранился бы, а история — нет. Поэтому `EditSession.apply` только
дописывает событие и сворачивает его редуктором, а **`undo()` и `redo()` тоже дописывают** обратные
события, а не вынимают из стека. Журнал остаётся следом того, что произошло, а не того, что осталось.

**Отмена восстанавливает документ точно.** Сравнивается не «тест прошёл», а весь `DocumentState` —
песня, штрихи, аннотации, текстовые метки: `DOC_EQUAL before_edit_and_after_undo = true`, и отдельно
— что в правленой ячейке снова исходный аккорд.

**Правка при транспозиции согласована по построению:** палитра рисуется в **показанной** тональности,
аккорд хранится звучащим корнем, страница рисует его в показанной тональности. Предпросмотр и
страница не могут разойтись, потому что считаются одинаково.

**Названо, а не спрятано:**
- **сам лист палитры не отрисовывался и не управлялся** — ни картинки, ни виджет-теста. Исполнением
  проверены палитра как список вариантов и сессия правки; сам виджет — только разбором и чтением;
- **undo не переживает переоткрытие файла.** Документ и журнал переживают, стеки отмены — нет:
  отменить правку, сделанную до открытия файла, нельзя. Это осознанно;
- **ячейка с парой аккордов на одной доле** (например `E7b5 A7` — шаги 0 и 1) достижима только по
  шагу 0: палитра правит нижний шаг и не умеет адресовать шаг 1. Это настоящее ограничение среза, а
  не дефект;
- переливка FIT при удлинении аккорда **измерена**, но не оценена на порог читаемости A30.

### A36 — что браузер на самом деле даёт перу: замер на планшете

Спайк-страница (`tools/web_pen_spike/`) прогнана **владельцем на планшете с S Pen**: 23 штриха,
1632 сэмпла, перо 1263 сэмпла, палец 369. Числа решают вопрос веб-пути.

**Работает:**

| Величина | Значение | Что значит |
|---|---|---|
| сэмплов на штрих | **71** | высокочастотный поток доходит до страницы — по сэмплу на кадр |
| различных значений давления | **65** | **давление настоящее**, а не константа; это была главная неизвестная |
| различных значений наклона | 4 | наклон приходит (в пробнике огрублён до шага 5°) |
| перо / палец | 1263 / 369, мышь 0 | перо и палец различаются чисто |
| **события наведения пера** | **215** | браузер отдаёт наведение — на этом и держится правило ладони для веба |
| ввод → отрисовка, p50 / p95 | **4.7 / 9.7 мс**, максимум 14.8 | **не сравнивать** с нативными 31.66 / 47.66: там мерился момент показа кадра, в браузере такого API нет |

**Второй прогон** (владелец, с ладонью, но **без пера в игре**): 5 штрихов, 12 сэмплов, `penSeen 0`,
наведение 0, давления и наклона по одному значению — то есть пера в нём не было вовсе, и он
показывает поведение **пальца и ладони**, а не пера. Именно он и дал ширины `71` и `87`.

**Не работает — и это главная находка, ПЕРЕСМОТРЕННАЯ ВТОРЫМ ПРОГОНОМ:** в первом прогоне ширины
касаний лежали в диапазоне `1..8`, перо ширину не сообщило, и `palmWouldReject` остался нулём. Из
этого я заключил, что **правило ладони по ширине на веб не переносится**. **Второй прогон это
опроверг:** без пера ширины касаний были `2,3,4,6,7` **и `71`, `87`** — то есть ширина есть, и
ладонь даёт тот же порядок, что на Android. Разделение `1..8` против `71..87` огромно.

**Что осталось неизвестным:** широкие касания в первом прогоне могли отсутствовать либо потому, что
ладонь не лежала на стекле, либо потому, что платформа подавила её при активном пере. **Эти два
объяснения числами не различаются**, и нужен отдельный прогон, где ладонь лежит **при рисующем пере**.

**Вывод и сделанное действие.** Правило берёт оба сигнала — приближение пера И ширину контакта — и
записывает, какой из них сработал. Проверено вождением: узкое касание без пера рисуется, широкое
отклоняется по ширине, узкое сразу после пера отклоняется по приближению. Окно «рядом» должно быть
**измерено** по промежуткам между событиями пера; страница печатает их процентили для этого.

**Не проверено:** iOS Safari — вообще. У владельца iPhone без Apple Pencil, и поведение `touch` в
Safari остаётся неизвестностью, которая решает, годится ли веб для iPhone.

### A37 — перо рисует в браузере: что Flutter Web отдаёт и чем это пришлось дополнить

**Сделано: режим рукописи на веб-цели.** Кнопка в верхней панели переключает режим; с ним перо
рисует, палец по-прежнему выбирает такт; без него перо выбирает наравне с пальцем. Завершённый
штрих становится `InkStroke` в якорной форме и дописывается в журнал операций как
`InkStrokeAddEvent`; отмена его убирает; штрих рисуется слоем поверх ча́рта, привязанным к ячейке
своего начала.

**Что Flutter Web отдаёт перу — измерено, а не предположено.** Прогон синтетического пера через
живую страницу, обе стороны одновременно: собственный слушатель на `document` (сырой поток) и
приложение (поток фреймворка). Числа с наведённого пера:

| величина | сырой поток браузера | поток фреймворка |
|---|---|---|
| `pressure` | **12 различных значений** на штрих, 0.00–0.85 | **2 различных** |
| `tilt` | приходит (`tiltX`/`tiltY`) | приходит (`PointerEvent.tilt`) |
| `pointerType` | `pen` / `touch` / `mouse` | `kind` = `stylus` / `touch` / `mouse` |
| `width` (геометрия касания) | **есть** — 1, 2, 3, 4 на узких касаниях | **0 — поля нет** |
| coalesced | счётчик есть, `coalescedPerEvent` 1.00 | не наблюдался выше 1 |

**Отсюда решение — и оно не одно и то же для разных полей.** Давление и наклон фреймворк отдаёт,
поэтому **своего слоя захвата для штриха не нужно**: рисование идёт через Flutter, без
`dart:js_interop` на пути каждой точки. А **ширину касания Flutter Web теряет вовсе**: его
`PointerBinding` собирает `PointerData` из позиции, давления, наклона и типа и никогда не читает
`event.width` из DOM. Поэтому ширина — второе слагаемое правила ладони A36 — до правила не
доходила, и узкая ветка правила на вебе не могла сработать в принципе. Дополнение сделано узким
ровно настолько: **тонкий наблюдатель**, пассивный слушатель на `document` в фазе перехвата,
который не вызывает `preventDefault`, не останавливает распространение и не строит штрих. Он
кладёт измеренную браузером ширину в очередь, и правило берёт её вместо нулевой ширины
фреймворка. Это та же форма, что на Android, где сырой поток даёт `PlatformView`.

**Порядок событий у этого моста не гарантирован, и это записано, а не спрятано.** Мост засеян
(наблюдались ширины 1 и 4, и `lastDecidingWidth` принимал их вместо нуля), но в одном прогоне
решение принималось раньше, чем приезжал сырой образец, и касание получало
`reason=width-not-reported` — то есть ширины на момент решения не было. Отказ в эту сторону
безопасен по построению: нераспознанное касание **выбирает**, а не рисует. Перо от этого не
страдает вообще — правило для пера ширину не читает.

**Почему ширина решает в пользу отказа, а не допуска.** Ширина — единственное, что отличает
кончик пальца от ладони: вид указателя называет и то и другое пальцем. Неизмеренная ширина не
может обосновать вывод «это можно рисовать», поэтому касание с неизмеренной шириной выбирает.
Правило, сделанное наоборот, дало бы размазанный ча́рт под рукой пишущего.

**Якорь выбран из формы штриха, а не из его рамки.** Якорь берётся по ПЕРВОЙ точке, потому что
размах штриха — не свидетельство намерения: штрих, вышедший за свою ячейку, был бы приписан
соседней, и ошибка всплыла бы только после транспозиции. Точка отсчёта — левый верхний угол
ячейки (или такта, если начало попало в отступ такта). Обратное преобразование живёт в одном
месте, `pagePointToAnchorLocal`, и оно же используется при отрисовке — двух путей арифметики нет.

**Отрисовка идёт по якорю.** `InkPainter` берёт сохранённые точки (они в логических пикселях
относительно якоря) и прибавляет к ним положение якоря НА ЭТОЙ странице, масштабируя холст ровно
так же, как `ChartPainter`. Один и тот же штрих поэтому остаётся на своём месте в музыке при
FIT, при транспозиции и после сохранения-чтения файла.

**Дефект, найденный только чтением собственного журнала на живой странице.** Штрих попадал в
журнал и не появлялся на экране: отмена была серой, а страница перерисовывалась только следующим
посторонним перестроением. Причина — порядок диспетчеризации: Flutter обходит путь попадания от
самого глубокого узла наружу, поэтому обработчик подъёма у слушателя выбора выполнялся РАНЬШЕ,
чем `endStroke` дописывал штрих, спрашивал у документа число штрихов, получал ноль и пропускал
перерисовку. В журнале это видно двумя строками подряд: `strokes=0 rebuild=false`, затем
`ink.stroke.commit`. Исправлено порядком виджетов: **слой рукописи снаружи, распознаватель тапа
внутри**. Жест разрешается только после того, как отработали все обработчики события, поэтому
`endStroke` успевает дописать штрих до решения о выборе. Порядок здесь несущий, а не
стилистический, и записан рядом с кодом.

**Отмена сравнивается не «сработала», а по документу.** В тесте виджетов после штриха в документе
один штрих и `undoDepth = 1`; после нажатия отмены — ноль штрихов и `undoDepth = 0`; повтор
возвращает ровно один. В браузере: до отмены `n = 1`, после — `n = 0`, `undo = 0`, `redo = 1`, и
на снимке штриха нет.

**Проверено вождением на живой странице:** штрих, нарисованный по ча́рту в браузере, лёг на
`sec-A-0, bar 0, beat 0` — то есть на такт, по которому целились, и виден на снимке поверх `C^7`.
Два PNG сняты и просмотрены (до и после отмены).

**Не проверено, названо:**
- **FIT-доказательство якоря в браузере не выполнено.** Снимок в режиме FIT делался, но сравнить
  положение штриха между обычной и ужатой страницей в браузере не удалось: синтетический
  `PointerEvent`, отправленный в страницу, доходит до фреймворка только как нажатие и отпускание
  без промежуточных точек, а настоящее касание через CDP даёт ширину касания не с первого раза —
  и то и другое описано выше. Доказательство якоря при FIT предъявлено headless-тестом

### A38 — форма песни и метаданные: два пробела найдены, названы и закрыты

**Сделано.** Относительно выделенного такта: вставить такт до и после, скопировать такт, удалить
такт. Для секции выделенного такта: вставить до и после, переименовать, скопировать, сдвинуть
раньше/позже, удалить. Всё это — один лист поверх ча́рта, открываемый двумя путями: переключателем в
верхней панели и строкой выделения, когда касание назвало **такт без ячейки**. Строка выделения
получила второе назначение именно потому, что такт без ячейки — это единственное выделение, у
которого раньше не было ни одного действия: палитра аккордов требует ячейки, а форме нужен такт.
Название, композитор, стиль и темп стали редактируемыми: лист «Song info» из строки заголовка, и он
же — с курсором в нужном поле — из полей BPM и STYLE сцена-бара, потому что мёртвый текст там был
видимым симптомом отсутствующего события.

**Что именно кладётся в событие, решается рядом с единственным писателем (`EditSession`).** Дубликат
секции обязан получить **новый** идентификатор: два раздела с одним id сделали бы неоднозначным
каждый якорь, который этот id называет. Новый такт наследует **метр** соседа и не наследует его
знаки: размер — свойство такта (в реальном ча́рте он меняется внутри песни), а повтор, вольта и
черта — знаки пассажа, и скопированный в произвольное место повтор сказал бы «играть отсюда» о
музыке, которая не повторяется. Новая секция всегда рождается с одним тактом, а последний такт
секции и последняя секция не удаляются: страница рисует секцию через её такты, поэтому секция без
тактов не видна, не нажимаема и выбрать её больше нельзя — состояние, достижимое одним нажатием и
необратимое. Отказ при этом **сказан на экране**, а не проигнорирован молча.

**Форма песни в каталоге уже была; метаданные — не были, и это пришлось расширить каталог.**
`measure.insert/delete/duplicate` и `section.insert/delete/update/duplicate/reorder` несли и событие,
и обратную половину, и для тактов и секций ни одного нового типа события не добавлено. А для
названия, композитора, стиля и темпа события не было ВООБЩЕ: все 32 типа в 12 семействах, и ни один
не несёт поля песни, а `SongEditing.copyWith` (`document_edits.dart`) принимает эти поля, но до него
не доводит ни одно событие. Первый заход это **нашёл и назвал, а не закрыл задней дверью** — прямая
правка `Song` сломала бы сразу отмену, повтор и хвост `.chart` (A35). Решением владельца каталог
расширен одним семейством: **`song.update`**, поля `{title, composer, style, tempo}`.

**`song.update` несёт все четыре поля С ОБЕИХ СТОРОН, и отсутствующее поле — типизированный отказ.**
Обратная половина — это тот же набор четырёх значений, переставленный местами, а не дельта: дельту
пришлось бы восстанавливать, а восстановленное значение можно восстановить неправильно (темп 0 не
оставляет, от чего отнять; пустое название — законное значение, а не отсутствие). Поэтому на проводе
всегда четыре поля, и `ModelJson.decodeSongMetadata` бросает `EventFormatException` на пропущенном
или неверно типизированном поле, а не подставляет умолчание: умолчание сделало бы обрезанное
событие неотличимым от правки, стирающей название. Частичная ПРАВКА выражается вызывающим, который
заполняет три поля из документа, — и одна такая правка пишется одним событием, поэтому «поправил темп
и заметил опечатку в названии» — это одна отмена, а не две. Правило закреплено там, где живёт весь
каталог: событие добавлено в `_chartEvents()` (`oplog_events_test.dart`) — от этого автоматически
проверяются круговорот JSON, строка `events.jsonl`, переномерование и свойство «событие + обратное =
исходный документ», — плюс литеральная строка в таблице закреплённых имён полей и отдельная проверка
на пропущенное поле. `chart_core`: было 271/3, стало **274/3**.

**НАЙДЕНО И ЗАКРЫТО: `.chart`, записанный кнопкой сохранения, применял свой хвост дважды.** На первом
заходе это было измерено и названо, а не исправлено: `chartFileFor` вызывался с ТЕКУЩИМ документом и с
журналом, который его же и произвёл, а контейнер определяет документ как «снимок ПЛЮС хвост» (A34).
На последовательности из семи правок это давало **4 секции / 16 тактов в файле против 6 секций /
24 тактов при чтении**; вставка удваивалась, удаление сносило соседний такт, а повторно применённый
штрих бросал `DocumentReducerException` — открытие ча́рта с рукописью падало с «Could not open».
Исправлено ровно по контракту A34, без нового замысла: `EditSession` теперь **применяет `restored` в
конструкторе** и помнит `baseDocument` — состояние ДО журнала; сохранение пишет «база + журнал», а
открытие отдаёт «снимок + хвост». `OpenedChart.document` — это снимок, а не свёрнутый документ; иначе
сессия применяла бы хвост к состоянию, которое его уже содержит.

**Почему проба этого не видела — и что из этого следует.** `probe_edit_loop.dart` сохранял хвост из
трёх `chord.update`, а они идемпотентны по адресу: применение дважды даёт правильный документ. Проба
была зелёной на свойстве, которого не проверяла. Поэтому обе пробы (`probe_chart_seam.dart`,
`probe_edit_loop.dart`) теперь несут хвост из **неидемпотентных** операций — удаление такта, вставка
такта, `song.update` и штрих, чья повторная запись отказывается outright, — и доказательство в них
это ОТКРЫТИЕ, а не арифметика: сессия, открытая из файла так, как это делает просмотрщик, обязана
держать сохранённый ча́рт (`REOPENED_DOCUMENT_EQUAL`; `probe_chart_seam` 29 проверок, `probe_edit_loop`
50 проверок, 0 отказов). В приборе `song_form_render_test.dart` рядом с этим стоит **отрицательный
контроль**: файл той самой прежней формы читается и даёт 16→24 такта и 4→6 секций, то есть проверка
открытия умеет падать. Без него «открылось равно» ничего не значит.

**Почему лист, а не строка кнопок над ча́ртом.** Урок A34 измерен: элемент в теле забирает у ча́рта
высоту, а FIT отказывается ужимать ниже порога читаемости. Оба входа высоты не занимают: лист
появляется только когда открыт, а переключатель живёт в панели, высота которой от действий не
меняется. Лист остаётся открытым после каждой операции и держит **собственный курсор**, потому что
каждая операция сдвигает тот самый адрес, по которому была сделана: вставка такта перед выделением
перемещает выделенный такт на место позже, а после удаления старый индекс называет уже другой такт.

высоту, а FIT отказывается ужимать ниже порога читаемости. Оба входа высоты не занимают: лист
появляется только когда открыт, а переключатель живёт в панели, высота которой от действий не
меняется. Лист остаётся открытым после каждой операции и держит **собственный курсор**, потому что
каждая операция сдвигает тот самый адрес, по которому была сделана: вставка такта перед выделением
перемещает выделенный такт на место позже, а после удаления старый индекс называет уже другой такт.

**Последний такт секции и последняя секция не удаляются, и это правило добавлено здесь.** Страница
рисует секцию через её такты: секция без тактов не видна, не нажимаема и выбрать её больше нельзя —
состояние, достижимое одним нажатием и необратимое. Поэтому «удалить такт» отказывает на последнем
такте секции, а «удалить секцию» — на единственной секции, и отказ **сказан на экране**, а не молча
проигнорирован. Следствие, названное: вставка секции всегда даёт секцию с одним тактом (иначе новый
элемент был бы недостижим по построению), а секция без тактов, пришедшая из чужой записи, редактору
недоступна и не создаётся им никогда.

**Проверено глазами и вождением.** Десять типов операций, каждая — PNG страницы до и после,
просмотрены; все «до» побайтово совпали отпечатком (`2ef56c61`), то есть фикстура действительно
восстанавливалась между случаями, а не выглядела похожей. Отмена после каждой операции сравнивает
**весь `DocumentState`** — `doc_equal=true` вместе с `song_equal`, числом штрихов, аннотаций и
меток; булево утверждение здесь только печатается рядом с полной выгрузкой секций. В браузере
(собранный `build/web`, headless): касание такта → `viewer.select … hit=sec-A-0#1 beat=0`; лист →
`viewer.form.op "Duplicated this bar." … bars=5 seq=1 undo_depth=1`; на странице видно пять тактов с
копией на месте второго; отмена → `viewer.undo done=true … redo_depth=1` и снова четыре такта.
Строка выделения с тактом без ячейки открывает тот же лист — это проверено отдельным касанием в
отступ такта (`hit=sec-A-0#1 beat=null`).

**Не проверено, названо:** перестановка секции перетаскиванием не сделана (только сдвиг на одну
позицию кнопками); переименование в пустое имя запрещено и на экране, и в сессии; ча́рты, записанные
ПРЕЖНЕЙ формой (снимок, уже содержащий хвост), остаются нечитаемыми — совместимость назад не
делалась, потому что различить «снимок до хвоста» и «снимок после хвоста» в файле нечем, а угадывать
по бар-каунту — это эвристика, которая однажды прочитает живой ча́рт вдвое.

**Записано рядом с кодом, а не здесь: как водить веб-цель курсором.** При включённых семантиках
Flutter Web клик по нажимаемому узлу приходит как тап В ЦЕНТР узла, поэтому прицеливание по ча́рту
требует семантик выключенных и сырых координат, а кнопки наоборот лучше нажимать через их
семантический узел. Начало системы координат страницы измеряется один раз на раскладку: на окне
1400×900 оно вышло `(261, 311)`, то есть ячейка, о которой приложение сообщает `(139.3, 72.0)`,
нажимается в `(400, 383)`. Оба числа — измерение ТОГО окна, а не константы; они и правило выше
записаны в документации `_pageGeometry` в `viewer_screen.dart`, где их прочтёт следующий, кто будет
водить приложение.

### A39 — порядок исполнения выведен, но навигация в него не входит

A13 постановил: хранится только написанная форма, порядок — производное. **Сама производная теперь
существует**: `derivePlayOrder(Song) → PlayOrder` в `song/play_order.dart`, чистая функция, без
Flutter и без `dart:io`, проверяемая под `dart test`.

**Форма вывода выбрана так, чтобы её можно было проверять, а не только показывать.** Каждая
сыгранная позиция несёт три разные вещи, и их смешение — источник тихой неправды:

| Поле | Что означает | Почему отдельно |
|---|---|---|
| `written` | такт **на странице** | это подсвечивает играющий курсор; такт `%` назван здесь |
| `source` | такт, чья **музыка звучит** | под `%` он другой, и потребитель, взявший `written` за звучащее, ошибётся молча |
| `passes` | **все** охватывающие проходы, снаружи внутрь | одного «текущего прохода» мало: у вложенного повтора их несколько одновременно |

Проходы публикуются отдельно ещё и потому, что требование «сделать число проходов явным» нельзя
выполнить, оставив его выводимым из чего-то другого.

**Неоднозначные случаи решены явно, каждый с напечатанным ответом:**
- `%` после `%` — цепочка прослеживается назад до первого такта, который пишет музыку; цикл
  невозможен, потому что каждая ссылка указывает строго назад;
- `%` первым тактом **песни** — позиция **сохраняется**, источник равен себе, и это **докладывается**:
  выбросить позицию значило бы укоротить исполнение молча; `%` первым тактом **секции** разрешается
  в последний такт предыдущей секции, потому что секции — метки на линейном потоке, а не стены;
- число проходов модель не хранит, поэтому проходов **два**, и `passCountBasis` честно говорит
  `assumedTwoPasses`, а не выдаёт допущение за знание;
- вольта только с номером 1 — проходов всё равно два, второй не выбирает ни одного такта, **играет
  ничего** и **докладывается**: пустой проход не должен исчезать молча;
- конец повтора без начала — обычная тактовая черта плюс сообщение; начало без конца — **один**
  проход плюс сообщение (повторять до конца песни значило бы выдумать пассаж);
- вложенные повторы: внутренний разворачивается целиком на каждом внешнем проходе;
- пустая песня и пустая секция — пустой порядок без сообщений: пустая секция это обычное состояние
  редактирования, а не ошибка.

**Свойство, которое было бы ложным при неверном выводе, и его фальсификация.** Мультимножество
**звучащих** тактов утверждается точно, а не «примерно»: у вольт это
`{0:2, 1:2, 2:1, 3:1, 4:1, 5:1}`. Проверено поломкой: наследование вольты отключено
(`brackets[node.index] = own`), и свойство **упало** —

```
Expected: {0: 2, 1: 2, 2: 1, 3: 1, 4: 1, 5: 1}
Actual:   {0: 2, 1: 2, 2: 1, 3: 2, 4: 1, 5: 1}
Which: at location ['3'] is <2> instead of <1>
+25 -3: Some tests failed.
```

— после отката `+28: All tests passed!`. **Фальсификацию я воспроизвёл сам, независимо от автора**,
включая откат с побайтовым совпадением: проверка, которую нельзя провалить, не является проверкой.

**Чего в выводе НЕТ, и это главное: навигации.** `D.C. al Coda`, `D.S. al Fine`, кода и фине
остаются дословным текстом и **не меняют порядок ни на одну позицию**. A13 отложил это из-за
отсутствия корпуса, и корпуса с тех пор не появилось. Потребитель, который предположит, что
играющий курсор пойдёт по «To Coda», ошибётся — и это записано, а не умолчано.

**Второй пробел: число проходов больше двух невыразимо.** Голый `:|` означает ровно два прохода,
больше — только вольтами. Событие для этого не добавлено сознательно: сперва пусть этого потребует
ча́рт.

**Слабое место, унаследованное от импортёра:** скобка вольты пишется парсером только на такте,
несущем `N`, поэтому вывод наследует скобку на протяжении до закрывающей черты. Именно это даёт
правильное чтение реального корпуса («первая концовка `D- G7` / вторая `D- G7`»), но это следствие
поведения импортёра, а не свойство модели.

### A40 — сохранение и открытие `.chart` в браузере: два механизма, и оба сказаны вслух

D20 постановил, что пользовательские данные живут **файлами**. На нативном пути это работало, в
браузере — нет: шов бросал, а элемент управления **прятался**, чтобы не притворяться работающим.
Теперь он работает, и показан.

**Механизм определяется возможностью, а не строкой user-agent.** Проверяется наличие
`showSaveFilePicker` на объекте `window`. Это **проверено фальсификацией**: у свойства удаляли
собственность, и тот же диалог менял текст с «This browser can re-write a chart file it has already
been given…» на «…cannot re-write a file in place, so every Save downloads a NEW copy». То есть
ветвление действительно идёт по возможности, а не по догадке о браузере.

**Две ветки ведут себя по-разному, и интерфейс это говорит, а не скрывает:**

| Ветка | Когда | Что происходит |
|---|---|---|
| перезапись на месте | `showSaveFilePicker` есть (настольный Chromium) | дескриптор кэшируется, второе сохранение **пишет в тот же файл** |
| скачивание | всё остальное, включая **Chrome на Android** и Safari | каждый раз новый файл |

**Скачивание проверено по-настоящему, от начала до конца.** Headless-браузер выбрал файл, сохранил,
а затем **открыл тот самый скачанный файл**: `bytes=3222`, `bars=4 operations=3 warnings=0`.

**Перезапись на месте проверена честно наполовину, и это сказано.** Настоящий системный диалог
headless-браузер показать не может: вызов принимается и тут же прерывается. Это доказывает, что
**форма вызова настоящим API принимается**, и что прерывание обрабатывается как отмена —
`chart.save.web.cancelled`, **без молчаливого скачивания**. Переиспользование дескриптора и запись в
поток проверены **заглушкой**: первое сохранение — 1 вызов выбора, 1 запись, 1 закрытие; второе —
**по-прежнему 1 вызов выбора**, 2 записи, 2 закрытия. Это и есть крючок для автосохранения из D20.

**Испорченный файл в браузере показывает типизированную ошибку на экране, а не «не удалось»:**

```
Could not open: the container declares 3222 bytes but this file ends at 1611
Could not open: the header does not match its CRC-32: recorded 140336592, computed 903433057
```

Ча́рт при этом не рисуется — `viewer.chart.open.refused` в журнале.

**Поправка к D20, полученная реализацией:** `showSaveFilePicker` есть **только в настольном
Chromium**. Chrome на Android перезаписи на месте **не имеет**, поэтому планшет попадёт в ветку
скачивания — и попадёт туда сам, без правки кода, потому что определение идёт по возможности.
Обещание «Chrome/Android — перезапись на месте» в D20 было неточным, и оно исправлено там же.

**Не проверено, названо:** настоящий диалог File System Access с последующей записью в дескриптор
(доказана только окружающая логика и форма вызова); **Safari и iOS — вообще ничем**, на этой машине
Safari нет, и код скачивания, который выполнил бы Safari, прогонялся в Chromium; Firefox; Chrome на
Android. **iPhone остаётся непроверенным.**

### A41 — повторы и вольты стали редактируемыми: где живут контролы и что решено про очистку

**Пробел, который эта запись закрывает.** `RepeatSetEvent` и `VoltaSetEvent` лежали в каталоге с
самого начала, сцена-бар печатал `3× · 4 volta · 17 %`, и **задать ни одного из этих знаков было
нечем**. Теперь они задаются: `EditSession` получил `setRepeatStart`, `setRepeatEnd`,
`setRepeatPrevious` и `setVolta`, а лист формы песни — группу `REPEAT` с четырьмя контролами.

**Почему контролы в листе формы, а не в сцена-баре и не вторым листом.** Повтор и вольта — это
**состояние на такте** (A14), и деривация читает их ровно оттуда, поэтому им нужен тот самый адрес
такта, который лист формы уже держит своим курсором (A38). Второй лист завёл бы второй механизм
выделения и второе место, где адрес такта может разойтись с тем, на что указывает палец. Сцена-бар
же — поверхность чтения на расстоянии руки: контрол в нём стоил бы высоты, а A34 и A38 уже измеряли,
что элемент в теле забирает высоту у ча́рта, и FIT отказывается ужимать ниже порога читаемости.

**Что решено про смысл знаков — и почему это решила деривация, а не UI.** Три формы, которые легко
было бы запретить, **не запрещены**, потому что `derivePlayOrder` уже отвечает, что каждая значит, и
**докладывает** об этом; запрет в UI был бы вторым ответом на тот же вопрос, живущим на правке
вместо чтения:

| Форма | Что говорит деривация | Что делает контрол |
|---|---|---|
| повтор без закрывающей черты | `repeatStartWithoutEnd`: пассаж играется **один** раз | ставит знак как просили |
| конец повтора без начала | `repeatEndWithoutStart`: черта играется как обычная | ставит знак как просили |
| вольта на такте вне повтора | `voltaOutsideRepeat`: скобка не выбирает ни одного прохода и игнорируется как скобка | ставит скобку как просили |

**Как работает очистка — и почему это две разные операции, а не одна.** Тактовая черта снимается
**нейтральным значением** `Barline.single`: у черты оно есть, потому что черта всегда есть. Вольта
снимается **удалением** (`to: null`), и обнуление её номером `0` было бы ошибкой: `Volta(0)` — это
**безымянная скобка**, которую страница рисует, и A12 уже зафиксировал, что это не то же самое, что
`volta == null` («скобки нет»). Поэтому «нет скобки» и «скобка без номера» в диалоге — две разные
кнопки, а не одно значение, изображённое двумя способами.

**Отказано ровно два, и оба — потому что их не прочтёт никто.** Отрицательный номер вольты: ни один
проход деривации не равен отрицательному числу, поэтому такт со скобкой `-1` **заглушил бы себя** —
это не знак, которого не бывает, а состояние, которое деривация превращает в тишину; и правка, у
которой обе половины равны, потому что это запись в журнале и предложение отменить то, чего не было.
`slashRepeat` (`p`) из UI **не выставляется сознательно**: R4 прямо говорит, что слэш-повтор
повторяет аккорд внутри такта и **не является вопросом порядка исполнения**, а эта группа — про
порядок. `RepeatSigns` переносит его через правку не тронутым.

**Согласие с деривацией доказано, а не предположено.** Прибор
`apps/mobile/test/repeat_controls_render_test.dart` водит **настоящие кнопки** листа — включая
диалог вольты — и печатает написанные знаки и трассу деривации в одном прогоне. Через контролы
построен ча́рт «такт 1 — начало повтора, такт 2 — конец повтора с `[1.`, такт 3 — `[2.`»:

```
repeat.agreement signs="A[0] open=repeatStart close=single previous=none volta=none
  | A[1] open=single close=repeatEnd previous=none volta=volta(1)
  | A[2] open=single close=single previous=none volta=volta(2)"
  sounding={1: 2, 2: 1, 3: 1, 4: 1} passages=1 pass_count=2 basis=voltaRequired
repeat.after passage start=1 end=2 passes=2 basis=voltaRequired crosses=false
```

Свойство — мультимножество **звучащих** тактов: такт 1 звучит на обоих проходах, такт 2 только на
первом, такт 3 только на втором, такт 4 один раз. `passCountBasis=voltaRequired`, а не
`assumedTwoPasses`, — то есть два прохода потребовала **скобка 2**, а не допущение. Расхождений и
докладов ноль: форма, которую пишут контролы, — это форма, которую деривация понимает без решений.

**Сцена-бар перестал быть украшением, и это проверено в браузере без перезагрузки.** `repeatSummary`
считает по документу **сессии**, поэтому поле следует за правкой в том же кадре: лист формы зовёт
`onChanged`, страница перестраивается. Прибор читает поле, **пока лист ещё открыт**, и получает
`none → 1× → 1× → 1× · 1 volta → 1× · 2 volta` по мере нажатий. Headless-браузер на собранном
`build/web` дал то же самое без единой перезагрузки: после трёх отмен — `["none"]`, затем redo —
`["1×"]`, ещё redo — `["1× · 1 volta"]`, и третий redo поля не меняет, потому что конец повтора в
сводку не входит.

**Строка «открыт .chart» печатала `Song(...)` вместо названия.** `chartFileBar` интерполировал
`Song`, то есть `toString()` всего объекта, в предложение, которое читает музыкант. Исправлено на
название через один общий `songDisplayTitle` (тот же `Untitled` для пустого названия, что и
`IRealSong.title`, — чтобы две копии одного запасного значения однажды не разошлись). В браузере:
`Opened "Test Tune" · 3 operation(s).`

**Проверено глазами.** PNG той же музыки до и после — `before@2x.png` (четыре такта в двух системах,
все черты одинарные, скобок нет) и `after@2x.png` (тот же ча́рт с толстой чертой и точками перед
тактом 1, знаком конца повтора с `[1.` после такта 2 и `[2.` над тактом 3); **fitted**-страница при
масштабе **0.7979** несёт те же знаки, а отчёт печатает гравированную и поверхностную рамку одной
ячейки — `(177.08, 46.0, 63.61, 52.0)` против `(141.29, 36.70, 50.75, 41.49)` при `×0.7979`, —
то есть геометрия fitted-страницы не молчит. Отмена после каждой из четырёх правок сравнивает **весь
`DocumentState`**: `restored_equal_before=true`, `song_equal=true`, `reapplied_equal_applied=true`.

**Не проверено, названо.** Цифра вольты выше 4 из UI недостижима — модель принимает любую
неотрицательную, но строки кнопок на любой номер никто не просил, и корпус такой вольты не показал.
Контрол на **телефонной** ширине прокручивается вместе с листом и нажимается, но проверялся только
на окне 1400×900 и в headless-прогоне, а не пальцем на телефоне. Возможность **перетаскивания**
скобки на соседний такт не делалась: вольта ставится на выбранный такт и снимается с него. И
отдельно: `percent`-контрол выставляет `%` по циклу off → один такт → два такта, но **сводка
сцена-бара считает `%`-такты по-прежнему только как чтение** — их правка не проверялась в браузере,
проверена прибором.

**Модель песни готова** и покрыта тестами: `Song` → `Section` → `Bar` → `BeatChord`, с размером,

**ИСПРАВЛЕНО: синтетические метрики текста больше не синтетические.** Здесь стояло, что движок
layout (A15–A17) «опирается на синтетические метрики текста», а подключение настоящего `TextPainter`
— работа бенча. Настоящая реализация есть и живёт в `chart_ui`
(`flutter_text_metrics.dart`), потому что измерение текста — единственное, что тянет за собой
Flutter; `chart_core` остаётся свободным от него через шов `TextMetrics`. Именно поэтому раскладка
проверяется под `dart test` без Flutter, а рендер — под `flutter test` headless.

**Функция развёртки порядка исполнения** (повторы + вольты → что музыкант реально играет) —
единственное, что модель сознательно не содержала: она хранит только написанную форму (A13).
**В работе на момент этой правки**, в `chart_core`, с обязательством напечатать трассы и решить
неоднозначные случаи явно, а не по умолчанию.

**Важная поправка по S1, полученная разведкой формата.** Ходячее представление, что тело
`irealbook://` — это base64, **неверно**. Тело — percent-encoded UTF-8; поле музыки несёт
10-символьный магический префикс `1r34LbKcu7` (именно 10, не 9 — ошибка на единицу молча
портит все аккорды в правдоподобно выглядящий мусор) и проходит через фиксированную перестановку
блоками по 50 символов (`obfusc50`, инволюция) плюс три текстовые замены: `Kcl`→`| x`, `LZ`→` |`,
`XyQ`→три пробела. Порядок обязателен: сначала перестановка, потом замены. Экспорт приложения —
это HTML с одной ссылкой `irealb://`, где песни разделены `===`, а последний сегмент — имя
плейлиста, а не песня. Также: `[` `]` — это двойные тактовые черты, а **повторы** — `{` `}`;
круглые скобки — альтернативный аккорд, а не добавленная ступень.

**Что из этой разведки остаётся непроверенным.** Обход `obfusc50` по байтам или по символам —
вопрос про **не-ASCII в поле музыки**; в реальных файлах там только символы аккордов, то есть ASCII,
поэтому проверка не представилась, а не «подтвердилась». Назначение поля 2 в 10-полевой раскладке
по-прежнему не выяснено. Оба вопроса остаются открытыми и названными: ни один из них не мешает
разбору работающих файлов, и ни один не должен считаться закрытым.

### Чего в этом репозитории НЕТ

**Нормативный ADDENDUM, включая рабочие пакеты `WP-00`…`WP-10`, в репозитории отсутствует.** Его
реестр решений воспроизведён в §9, потому что документ должен читаться сам по себе, но **перечня
работ в нём нет** — поиск по всему репозиторию не находит ни одного упоминания `WP-`. Следствие
прямое: **плана работ нет нигде, кроме переписки**, и сопоставить сделанное с нормативным перечнем
нельзя. Либо ADDENDUM должен лежать здесь, либо перечень работ должен быть перенесён в §9 — но пока
не сделано ни то, ни другое, и единственная запись о том, что построено, — это журнал решений A.
